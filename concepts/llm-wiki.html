LLM-Wiki

2026-09-03 — 🚨 이 볼트에 결측된 층이 확인됐다: 검색 피드백 루프 (CoGR)

CoGR(HF 데일리 4위)은 검색을 이렇게 재정의한다 — 질의뿐 아니라 「아이템 측」의 검색 표현(키워드)도 LLM이 생성하고, 그 표현을 「질의 성공률의 반사실적 변화」로 학습시킨다. 이 볼트가 정확히 그 구조다. 915+개 소스 페이지를 grep과 wikilink로 찾고, 각 페이지의 태그·제목·wikilink가 곧 아이템 측 생성 키워드다 — 다만 내가 수작업으로 생성한다. 🚨 그런데 볼트는 그 키워드가 유효했는지 한 번도 측정한 적이 없다. 태그를 붙이기만 하고, 어떤 태그로 실제 페이지가 찾아졌는지 기록하지 않는다. CoGR의 표현을 빌리면 아이템 측에 보상 신호가 전혀 안 들어온다. 원인이 구조적이다: queries/ 디렉터리가 0건이다. 스키마에 “좋은 답변은 queries/에 저장” 이 있으나 한 번도 실행되지 않았다. 즉 볼트는 인제스트(쓰기)만 하고 쿼리(읽기)를 기록하지 않는 半쪽 시스템으로 5개월을 운영됐다. → actionable 등재(우선순위 높음): 쿼리를 queries/에 남기기 시작한다. 그것 없이는 어떤 태그가 죽은 태그인지 영원히 알 수 없다. 📌 같은 배치 Repo-To-Skill이 자산 5,000개를 만들고도 검색 방법을 안 적었다는 사실과 짝을 이룬다 — 자산을 쌓는 쪽은 찾는 문제를 늦게 발견한다. 볼트도 같은 순서를 밟고 있다.

LLM을 활용하여 개인 지식베이스를 복리 축적형으로 구축하는 패턴. Andrej Karpathy가 2026년 공개한 아이디어 가이드에서 비롯됨.

핵심 철학

기존 RAG 방식은 쿼리마다 원본에서 재추출한다 — 지식이 쌓이지 않는다. LLM-Wiki는 다르다: LLM이 영속적 위키를 점진적으로 구축·유지한다.

“The wiki is a persistent, compounding artifact. The cross-references are already there. The contradictions have already been flagged.” — Karpathy

인간의 역할: 소싱, 탐색, 좋은 질문 LLM의 역할: 요약, 교차 참조, 정리, 북키핑 전체

3계층 아키텍처

레이어소유자역할
Raw Sources인간원본 소스. 불변. 진실의 원천.
WikiLLM마크다운 파일 모음. LLM이 작성·유지.
Schema인간+LLMCLAUDE.md — LLM을 위키 관리자로 만드는 설정

3가지 핵심 작업

Ingest (인제스트)

새 소스 추가 → LLM이 읽고 → 위키에 통합

  • 단일 소스가 10~15개 페이지에 영향 가능
  • entity 페이지, concept 페이지, 모순 표시 등 자동화

Query (쿼리)

위키 대상으로 질문 → LLM이 관련 페이지 탐색 → 인용 포함 답변 합성

  • 좋은 답변은 위키 페이지로 보존 → 탐색 자체도 지식 복리 축적

Lint (린트)

주기적 위키 건강 점검:

  • 페이지 간 모순
  • 고아 페이지 (인바운드 링크 없음)
  • 낡은 주장 (최신 소스에 의해 대체됨)
  • 자체 페이지 없는 중요 개념

왜 작동하는가

“LLMs don’t get bored, don’t forget to update a cross-reference, and can touch 15 files in one pass.”

지식베이스 유지의 핵심 장벽은 북키핑 — 교차 참조 업데이트, 요약 최신화, 모순 표시. 인간은 이 부담이 커지면 위키를 포기한다. LLM은 지루함을 모르고 한 번에 15개 파일을 처리한다.

Vannevar Bush의 Memex와의 연결

1945년 Vannevar Bush가 꿈꾼 Memex — 개인적·능동적으로 큐레이션되며, 문서 간 연결이 문서 자체만큼 가치 있는 지식 저장소. Bush가 해결 못한 “누가 유지 관리하는가” 문제를 LLM이 담당한다.

  • Obsidian: 위키 뷰어. 그래프 뷰, Dataview 플러그인, Marp 슬라이드
  • Obsidian Web Clipper: 웹 기사 → 마크다운 변환
  • qmd: 위키용 로컬 검색 엔진 (BM25+벡터 하이브리드)
  • Git: 버전 관리, 브랜칭, 협업

2026-08-28 — 이 패턴이 설치 가능한 레포가 됐다 (첫 직접 비교군)

claude-obsidian(AgriciDaniel/claude-obsidian · ⭐14,215 · 포크 1,432 · MIT · Python · GitHub 트렌딩 14위)이 README에서 명시적으로 밝힌다 — “Based on Karpathy’s LLM Wiki pattern”.

스택까지 이 볼트와 동일하다: Obsidian + Claude Code + 순수 마크다운. 설계 주장도 겹친다 — “임의의 소스를 투입하면(drop any source) 읽고 · 링크하고 · 정리한다”, “당신이 소유하는 하나의 연결된 순수 마크다운 지식그래프”.

이건 벤치마킹 대상이 아니라 대조군이다

같은 패턴을 남이 구현했을 때 무엇이 자동화됐고 무엇이 여전히 판단으로 남았는지가, 이 볼트 인제스트 루프의 자동화 가능 상한을 알려준다. 확인할 세 가지: (1) 소스 투입 → 페이지 생성까지 사람 개입 지점 (2) wikilink를 무슨 근거로 만드나(문자열 매칭 / 임베딩 / LLM 판단) (3) 신규 페이지 vs 기존 갱신 판정을 자동화했나. (3)이 특히 중요하다 — 이 볼트에서 매 인제스트마다 손이 가장 많이 가는 판단이 정확히 그것이고, 900페이지가 넘는 규모에서 확장 한계에 부딪히는 지점도 그곳이다.

자동화된 지식그래프의 진짜 실패 모드는 "안 도는 것"이 아니다

claude-obsidian은 정리 정확도를 재는 수치를 제시하지 않는다. 그런데 지식그래프 도구의 지배적 실패는 동작 실패가 아니라 그럴듯하게 잘못 연결하는 것이고, 그건 스타 수로 절대 드러나지 않는다. 같은 날 배치의 PAWBench·FrontierChallenge가 겨누는 지점과 정확히 동형이다 — 산출물이 존재한다 ≠ 산출물이 옳다. 이 볼트가 이미 하고 있는 방어: > [!warning] 로 미검증 주장 분리 · API 실호출 재검증 · raw 수집 메모와 볼트 관측 계열이 충돌하면 볼트 계열을 정본으로 채택(2026-08-28 Qwen3.8-27B 사례). 자동 도구가 이런 판단을 하는지가 비교의 핵심이다.

이슈 밀도 관측: 이슈 140 / 포크 1,432 = 0.098건/포크로 08-28 배치 GitHub 5건 중 최고(awesome-gpt-image-2 0.0072의 13.6배). 볼트 규칙대로면 가장 “실행되는 소프트웨어”에 가깝다는 뜻이나, 마찰의 성격(버그 vs 기대 불일치)은 이슈 내용 미확인이다.

llm_wiki (⭐18,381·GPL-3.0) — 이 패턴의 앱 단계

계보가 3단계를 다 채웠다: 프롬프트 규약(llm-wiki-karpathy-2026) → 패키지(claude-obsidian) → 완제품 앱(llm_wiki). PDF·오피스·EPUB·이미지를 2단계 CoT로 인제스트, entity/concept 페이지 자동 생성, Rust 백엔드 챗 에이전트가 로컬 SKILL.md 를 읽는다.

🪞 볼트에 없는 것이 정확히 드러났다 — 그래프를 측정하지 않는다

llm_wiki가 가진 것(README 146~170행 원문):

  • 4-신호 관련성 모델: 직접 링크 · 출처 중첩 · Adamic-Adar ×1.5(공통 이웃을 이웃 차수로 가중) · 타입 친화도 ×1.0
  • Louvain 커뮤니티 탐지 + 응집도 점수화: “intra-edge density (actual edges / possible edges); low-cohesion clusters (< 0.15) flagged with warning”
  • 예상 밖 관계 탐지: cross-community edge · cross-type link · 주변↔허브 결합

이 볼트가 가진 것: grep -rl "\[\[페이지\]\]" | wc -l → 고아 페이지 카운트 하나. → 🎯 소스 1,012개를 쌓는 동안 링크 구조를 한 번도 정량 측정한 적이 없다. → 내 lint는 차수 0만 잡는다. 차수 1짜리 죽은 클러스터, 끊어진 도메인 간 다리, 연결됐어야 하는데 안 된 쌍은 전부 보이지 않는다. → synthesis/ 가 2건뿐인 이유가 이것이다 — 교차 연결을 찾는 절차가 없어서 사람이 눈으로 볼 때만 생긴다.

🔴 최우선 — lint를 측정으로 교체

외부 앱 이관은 불필요하다(볼트는 이미 Obsidian 포맷, 에이전트가 직접 쓴다). 알고리즘만 이식한다. 입력([[링크]] 그래프)은 이미 있다:

  1. 인접행렬 추출 (기존 grep -roh 재사용)
  2. Adamic-Adar 상위 20쌍 = “연결됐어야 하는데 안 된 쌍” → synthesis/ 후보 자동 생성
  3. 커뮤니티별 intra-edge density, <0.15 경고 → 죽은 클러스터 탐지 → 이것이 검사가능성-공사 가 요구한 외부 정답 고정의 6번째 형태 = 자기 그래프의 정량 지표다. 재료는 다 있고 측정만 없다.

이식 시 주의

4-신호 가중치의 근거가 README에 없다(Adamic-Adar ×1.5, 타입 친화도 ×1.0). 튜닝값인지 임의값인지 불명 → 그대로 베끼지 말고 내 그래프에서 재조정할 것.

🪞 볼트의 결측이 또 하나 드러났다 — 되돌리기가 없다

WeKnora가 가진 것:

  • v0.5.0 Wiki Mode GA — 상호링크 마크다운 + 지식그래프 + 그래프 뷰어
  • v0.5.2 위키 인제스트가 4만 문서 KB까지 확장(태스크 큐 + DLQ)
  • v0.7.2 위키 페이지 리비전 히스토리 — 스냅샷 + 행 단위 diff + 원클릭 롤백

볼트가 하는 것: 기존 페이지 하단에 ## 🔄 갱신 섹션을 덧붙인다. 그래서:

  • 틀린 판정을 되돌릴 수단이 없다. 09-11에 SenseNova-U1.5 판정이 틀렸다고 볼트 스스로 기록했지만 그 문장은 아직 페이지에 있다 — 반박 문단이 붙었을 뿐이다.
  • 페이지가 단조 증가한다. i-have-adhd 가 지적한 비대화(09-11 배치 평균 6.3KB)의 구조적 원인이 이것이다. 삭제 경로가 없으면 길어질 수밖에 없다. → 🎯 WeKnora가 롤백을 v0.7.2에서 별도 기능으로 낸 것은, 자동 생성 위키에서 “잘못 쓴 것을 지우는 문제”가 실제로 발생한다는 외부 증거다. 볼트는 그 문제를 겪지 않은 게 아니라 대응 수단이 없어 누적하고 있다. → 그리고 볼트에는 git 이 이미 있다(스키마 실용도구 항목에 명시). 없는 것은 도구가 아니라 규율이다.

🔴 그런데 hyperresearch 가 드러낸 것이 더 아프다 — 출고 전 검사가 0개다

hyperresearch는 리포트 출고 전 검증 배터리를 자동 실행한다(README 228·235·236행 원문):

  • quote-integrity — “every quoted span must exist verbatim in a vault note”
  • retracted-citations — 철회 논문 인용 시 출고 차단
  • numeric-consistency — 증거로 추적 안 되는 숫자 플래그
  • locus coverage — 논점마다 중간 노트 없으면 에러
  • patch-only — 최종 3단계는 툴 권한이 [Read, Edit] 로 잠겨 재생성이 물리적으로 불가능

🎯 볼트의 만성 지적 세 개가 여기서 한 문장으로 합쳐진다:

  • 검사가능성-공사 — “외부 정답 고정이 없다”
  • llm_wiki 갱신 — “그래프를 측정하지 않는다”
  • i-have-adhd — “쓰기는 매일 하고 자기 산출물을 읽고 고치기는 한 번도 안 한다” → 전부 「출고 전 자동 검사가 0개」라는 같은 사실의 다른 얼굴이다. → 그리고 볼트는 매 배치 “원문 대조 완료” 를 주장하는데 그 주장 자체가 한 번도 검사된 적이 없다.

🔴 최우선 — quote-integrity 1개만 이식한다 (AgentGrad 순차 개입)

6개 검사 중 1개만 고른다. 이유: 구현이 가장 싸고(인용 문자열 grep), 볼트의 핵심 주장을 직접 겨눈다. ⚠️ 오늘 배치가 이미 이 검사의 한계도 알려줬다 — 한정어-탈락 개념 참조. raw의 hyperresearch 인용은 원문에 글자 그대로 존재했지만 불완전했다(면책이 6행 아래에 더 세게 있었다). 존재 검사만으로는 못 잡는다. → 그래서 규격을 이렇게 정한다: ① 인용문이 원문에 존재하는가 ② 인용문 ±10행에 그 주장을 한정하는 문장이 있는가. 판정 기준(다음 배치): 소스 페이지의 직접 인용 중 원문 미검증 건이 0인가. 나머지 개입 — WeKnora 발 git 리비전 규율, llm_wiki 발 Adamic-Adar 그래프 측정 — 은 대기열에 두고 이번엔 건드리지 않는다.

아직 답이 없는 것 — 그런데 후보가 생겼다
