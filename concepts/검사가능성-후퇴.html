검사가능성 후퇴

정의

검사가능성을 가장 강하게 내세우는 쪽이 가장 검사 불가능한 아티팩트를 출하한다. 검사가능성-공사 가 “확인되지 않음 칸을 만드는” 수렴이라면, 이건 그 반대 방향이고 같은 배치에서 두 건 나왔다.

사례 1 — Ternary-Bonsai-2-27B: 벤더가 자기 eval 산출물을 뺐다

볼트 HF API 파일트리 실측:

  • v1 prism-ml/Ternary-Bonsai-27B-gguf → .eval_results/aime_2026.yaml · .eval_results/gsm8k.yaml · .eval_results/mmmu_pro.yaml + eval-results 태그
  • v2 prism-ml/Ternary-Bonsai-2-27B-gguf → .eval_results/ 없음 · eval-results 태그 없음

🔴 주장은 올라가고(80.49 계열 → 84.78 / 95% → 98.2%) 증거 산출물은 사라졌다. 남은 근거는 GitHub의 PDF 화이트페이퍼 1개뿐이다. 🎯 그리고 같은 README가 남의 라벨을 정밀하게 고발한다 — “a widely-used ‘2-bit’ build of Qwen3.8-27B is really 2.8 bits/weight at 9.4 GB”. 측정 규율을 남에게는 적용하고 자기 산출물은 뺐다.

사례 2 — Agora: “체크아웃 가능한 커밋”을 논지로 삼은 논문의 레포에 코드가 0개다

논문 초록: “research is recorded as an append-only DAG stored in Git, so that every claim is a commit anyone can check out and rerun.” 볼트 GitHub contents API 실측(master): LICENSE · README.md · assets/ · index.html. language: HTML. ★59. 🔴 본문 목차에 §3.4 Prototype implementation 이 있다 — 프로토타입은 존재하고, 공개되지 않았다. 🔴 1,703개 기여와 165건 독립 재현이 담긴 원본 DAG도 레포에 없다.

🎯 두 사례의 공통 구조

주장의 강도와 증거의 강도가 반대로 움직인다. 그리고 둘 다 “증거를 어떻게 다뤄야 하는가”를 문서에 적어 둔 쪽이다 — Bonsai는 비트수 라벨 규율을, Agora는 재현 요구사항(부록 A)을. 🎯 규율을 아는 것과 자기에게 적용하는 것이 다르다.

📌 검사가능성-공사 와 짝을 이룬다:

  • 공사 방향: security-audit-skill needs_validation(“no severity”) · oh-my-hermes Code · reported done · Agora 의 verification status 인덱스
  • 🔴 후퇴 방향: Bonsai v1→v2 · Agora 레포
  • 🎯 Agora는 양쪽에 동시에 있다 — 설계는 공사, 출하는 후퇴. 이게 이 개념의 가장 정확한 그림이다: 후퇴는 나쁜 의도가 아니라 우선순위의 결과다.

판별 절차 (볼트 규약)

주장이 강한 아티팩트를 받으면 주장이 아니라 파일 목록을 먼저 센다:

  1. 이전 버전과 파일트리를 비교한다 — 있다가 없어진 증거 파일이 있는가.
  2. 레포 최상위에 코드가 있는가 — LICENSE/README/assets/*.html 뿐이면 코드 0.
  3. 태그 변화(eval-results 등)를 본다 — 메타데이터가 먼저 빠진다.
  4. 🔴 “화이트페이퍼 PDF 1개”는 단일 출처다. 기계판독 산출물이 없으면 reliability 를 올리지 않는다.

🔴 한계

표본 2, 같은 배치. 의도를 추정하지 않았다 — 왜 뺐는지(포맷 변경? 미완? 정책?) 어느 쪽도 확인하지 못했다. Bonsai 쪽은 “32k 열은 런이 끝나면 채운다” 식의 설명이 없었다(Swift-Qwen3.8-27B-GGUF 는 그 설명을 달았다 — 같은 배치에 좋은 대조군이 있다).

2026-09-26 갱신 — 🔴 볼트 자기정정: 후퇴의 범위를 과잉 일반화했다

Ternary-Bonsai-2-27B 에 대해 볼트는 09-20에 이렇게 적었다: “같은 벤더가 더 좋은 점수를 주장하면서 기계판독 가능한 평가 산출물을 뺐다. 근거는 이제 GitHub의 PDF 화이트페이퍼 한 개뿐이다.”

오늘 카드 311행 전문을 열어 확인한 결과 — 앞 문장은 맞고 뒤 문장은 틀렸다.

  • ✅ 맞음: .eval_results/ 없음 · eval-results 태그 없음(09-26 HF API 파일 11개 전수 재확인, eval 관련 0건). 기계판독 산출물 제거는 사실.
  • 🔴 틀림: 카드 본문에 표가 3개 있다 — 219220행 비교 표(IQ2_XXS 72.59 vs Bonsai 84.78) · 231236행 카테고리별 baseline 대조 표(Overall 86.32→84.78) · 205행 처리량 표(47.0 tok/s). v1에 없던 baseline 열까지 붙어 있다.

🎯 정확한 진술 — 기계 대조는 후퇴했고 사람 대조는 전진했다

이 개념은 “기계판독 산출물의 제거”에 한정해야 한다. “주장을 대조할 수 없게 됐다” 로 확장하면 틀린다. 두 축을 분리한다:

  • 기계 검사가능성: .eval_results/ · model-index · eval-results 태그 → 후퇴함
  • 사람 검사가능성: 카드 본문의 baseline 대조 표 → 개선됨

📌 오류의 형태가 09-24와 같은 계열이다. 09-24엔 NOASSERTION 한 값이 두 실체(커스텀 / 탐지실패)를 접었고, 오늘은 볼트가 “한 축의 후퇴”를 “전 축의 후퇴”로 접었다. 둘 다 해상도가 낮은 판정이 서로 다른 상태를 한 칸에 몰아넣는 문제다. ⚠️ 대비 개념: 처음부터 이미지로만 낸 경우는 후퇴가 아니라 벤치마크-이미지-봉인 이다. 시간적 변화(후퇴)와 정적 형식(봉인)을 구분한다.
