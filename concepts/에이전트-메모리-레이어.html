2026-09-03 — 네 번째 방식: 「선택적 비독해」(Declarative-Attention)

이 페이지는 메모리 처리를 RAG(외부 검색) · KV 캐시 · 압축 · 외부DB 로 분류해 왔다. 이번 배치의 Declarative-Attention(HF 데일리 5위)이 어디에도 안 들어가는 방식을 보였다. 외부에 두지도, 압축하지도 않는다. 읽지 않기로 선택한다. 모델이 사고사슬 안에서 <global>/<focus>/<local> 로 참조 범위를 스스로 선언하고, 추론 엔진이 이를 툴콜처럼 파싱해 KV 캐시 읽기를 건너뛴다. 15개 롱컨텍스트 과제 제로샷: Gemma-4-31B 참조 토큰 -52.0%(정확도 -1.27%p) · Qwen-3.6-27B -31.1%(-2.75%p). 학습 불필요 · 기성 모델 적용.

📌 분류축이 바뀐다. 기존 넷은 전부 “기억을 어디에 어떤 형태로 두는가” 를 나눈다. 이건 기억을 그대로 두고 「읽기 결정」만 모델에게 넘긴다. → 관련성 판단의 주체가 바뀐 것이 핵심이다: RAG는 검색기가, 프록시 점수 방식은 외부 스코어러가, 이건 모델 자신이 판단한다. 논문의 동기 질문이 그대로다 — “모델이 이미 어느 부분이 관련 있는지 알고 있지 않겠는가?” 볼트 함의: 내 Hermes 장기 세션에서 KV 캐시가 병목일 때 엔진 수정 없이 프롬프트 층에서 흉내낼 수 있다 — 답변 전에 “최근 대화만 보면 되는가, 전체를 봐야 하는가” 를 선언시키고 컨텍스트 주입량을 그에 맞춰 바꾸는 형태. 이득은 작지만 비용이 0이다. → actionable 등재. ⚠️ -52.0%는 참조 토큰이지 wall-clock이 아니다. 실제 속도 이득은 미확인이고, 추론 엔진 수정이 전제라 vLLM/llama.cpp에 바로 얹히지 않는다.

2026-08-26 — 갱신 승인 조건이라는 새 분류축 (Recuris)

이 페이지는 지금까지 메모리를 저장 방식(RAG / KV / 압축 / 외부DB)으로 분류해 왔다. Recuris(HF 데일리 5위·업16·코드 공개·초록 원문 실검증)가 그 축만으로는 못 잡는 차원을 드러낸다 — “무엇을 언제 메모리에 반영할 것인가”. Recuris의 3층 구조는 저장 위치가 아니라 역할과 승인 절차로 갈린다:

  • Working Memory — 태스크 진행 상태 추적. 스킬 선택의 근거를 전체 히스토리가 아니라 현재 필요로 바꾼다.
  • Experiential Memory — 축적된 경험 풀. Working Memory가 여기서 스킬을 고른다.
  • Skill Memory — 검증 게이트를 통과한 갱신만 반영된다. Meta-Agent가 실행 증거를 국소 패치로 변환.

핵심은 검증 게이트다. MemTrapBench가 보고한 “평가된 5개 메모리 프레임워크가 전부 no-memory보다 못했다” 는 결과의 원인이 무조건 축적으로 인한 오염이라면, 게이트는 정확히 그 지점을 겨눈다. 실측은 이를 지지한다 — 4벤치×10모델의 완료된 37쌍 중 35쌍 개선, tau-bench에서 Claude Opus 5 +15.6점(87.9%), 가장 긴 태스크 +32.2점, 흔한 롱호라이즌 실패 최대 80% 감소. “지평이 길수록 이득이 커진다”가 이 축의 서명이다 — 기존 메모리 기법 다수가 긴 태스크에서 무너지던 것과 반대 방향이다. 그리고 프런티어 모델(Opus 5)에서도 두 자릿수 개선이 나온다는 건 모델 성능이 올라도 메모리 구조가 남긴 여지는 줄지 않는다는 뜻이다.

⚠️ 미해결: 검증 게이트의 판정 기준이 초록에 없다. Thinkingbox가 실증한 “깨끗한 종료가 완수를 뜻하지 않는다” 를 감안하면, 게이트가 exit code·에러 유무류 신호를 쓰면 오염을 거르지 못한다. Meta-Agent 호출 비용도 미기재라 짧은 태스크에서의 손익은 계산 불가.

2026-08-24 — 이벤트 소싱 계열 대안 편입 ( apache-maka)

MemTrapBench가 제기한 오염 문제에 대해 다른 층위의 답이 들어왔다. apache-maka(Apache Software Foundation 인큐베이팅·⭐2,497·Apache-2.0·README 원문 실측)는 메모리를 요약해서 다시 주입하는 것으로 보지 않고, 기록과 주입을 분리한다.

  • 모델 메시지·툴 호출·툴 결과·권한 결정·종료 이벤트를 append-only 로그로 남긴다. UI와 다음 모델 호출은 그 기록의 뷰(view) 일 뿐 유일한 사본이 아니다.
  • README 원문의 핵심 문장: “Shorter context is not deleted history” — 다음 프롬프트에서 오래된 툴 출력을 생략하되 저장된 증거는 버리지 않는다.

왜 중요한가: 이 페이지가 쌓아 온 메모리 구현 대부분은 “무엇을 저장하고 어떻게 검색할까” 를 최적화했고, MemTrapBench는 바로 그 저장·검색이 충실할수록 오염이 함께 주입된다는 것을 보였다. 이벤트 소싱 접근은 불변 기록(감사 가능성) 과 선택적 주입(오염 최소화) 을 분리해, 오염원을 줄이면서 사후 추적성을 잃지 않는다. 메모리 축의 설계 선택지가 “저장 방식” 에서 “기록과 컨텍스트의 분리” 로 한 단계 넓어졌다. ⚠️미해결: 어떤 툴 출력을 생략할지 선택하는 기준이 곧 MemTrapBench가 지적한 왜곡 지점이며, 그 기준이 규칙 기반인지 학습 기반인지는 미확인이다. 또한 append-only 로그의 용량 증가 대책·샌드박스 격리 수준도 미확인. 실용 제약으로 Linux 미지원(macOS arm64 초기 릴리스·Windows 서명 없는 프리뷰)이라 내 환경에서 즉시 실행 불가 — 설계(ARCHITECTURE.md) 참조 대상이다. 같은 배치 Graph-Engineering은 지속 상태를 그래프로 표현하자고 제안하는데, 이는 로그 표현과 경쟁 형식이며 어느 쪽이 나은지 비교 실험은 아직 없다.

2026-08-22 — 이 개념의 핵심 전제에 대한 첫 정량 반례 ( MemTrapBench)

이 페이지가 OpenViking·ai-memory·MobileMem 등으로 누적해 온 암묵 전제는 “에이전트에 메모리를 붙일수록 좋다”, 그리고 “메모리 품질 = 저장·검색 정확도” 였다. 2026-08-22 편입한 MemTrapBench(HF 데일리 6위·업31·초록 원문 실검증)가 이 둘을 정면으로 반박한다.

  • memory-induced cognitive traps(메모리 유발 인지 함정) 을 정의 — 충실히 기록되고 의미적으로도 관련 있는 메모리조차 추론·믿음을 왜곡한다. 두 형태: Reasoning Fixation(추론 고착), Belief Distortion(믿음 왜곡).
  • 2개 모델 패밀리 × 5개 대표 메모리 프레임워크 실험에서 평가된 모든 메모리 전략이 “메모리 없음(no-memory)“보다 못했고, 최강 방법도 10% 이상 하락.
  • 완화책 AdaptiveMem — 추론 시점에 LLM에게 메모리 함정을 피하도록 지시하는 단순 방법으로, 표준 메모리 벤치 성능은 보존·개선하면서 함정만 완화.

개념 수정: 메모리 레이어를 평가할 때 “저장·검색이 정확한가”만으로는 불충분하며, “검색된 메모리가 현재 태스크 추론을 오염시키지 않는가” 가 별도 축으로 필요하다. 실무적으로는 메모리 도입 시 ON/OFF A/B를 필수 관문으로 둘 것. ⚠️단, 5개 프레임워크·2개 모델 패밀리라는 표본 범위와 MemTrapBench가 함정을 겨냥해 설계된 적대적 벤치라는 점을 감안해야 한다 — “메모리는 해롭다”로 일반화 금물. 정확한 주장은 “현행 메모리 전략들은 자신이 유발하는 추론 오염을 측정도 통제도 하지 않는다”.

대응 축: 에이전트-스킬이 절차 지식의 유지·진화 문제(SkillEvo)를 다룬다면, 이 페이지는 경험 지식의 오염 문제를 다룬다.

핵심 인사이트

2026년 4월 기준, 에이전트 인프라는 “코어 실행 레이어 + 메모리 레이어” 2계층 구조로 표준화되고 있다. hermes-agent·superpowers 같은 실행 프레임워크가 정착한 이후, 다음 경쟁은 어떻게 기억하고 맥락을 유지하는가로 이동 중.

2026-08-25 — 메모리도 평가 축이 됐다

"메모리 사용"이 채점 항목으로 명시됐다 ( MobilePA-Bench)

MobilePA-Bench(HF 데일리 2위·2026-08-24)는 메모리 사용(Memory Usage) 을 상위 평가 차원으로 두고, 구체적으로 “저장된 메모리·사용자 프로필·과거 선호를 되살려 암묵적 요청(implicit requests)을 해소하는가” 를 본다. 주목할 정의: 메모리 평가의 기준이 “얼마나 많이 저장했나”나 “얼마나 정확히 회상하나”가 아니라 “사용자가 말하지 않은 것을 채워 넣는가” 로 잡혔다. 메모리의 가치가 저장·검색 성능이 아니라 대화의 생략을 복원하는 능력으로 조작적 정의된 것이다. 에이전트-스킬도 같은 논문에서 나란히 평가 축으로 승격됐다.

MemTrapBench의 경고와 함께 읽어야 한다

이 개념 페이지는 이미 MemTrapBench(평가된 5개 메모리 프레임워크 전부가 no-memory보다 못했음)를 기록하고 있다. 이번 배치는 그 긴장을 해소하지 않는다 — 메모리를 평가 축으로 세우는 흐름과 메모리가 오히려 해가 된다는 증거가 동시에 존재한다. 정합적 해석: 메모리 유무가 아니라 메모리 사용의 질이 문제라는 것. MemTrapBench가 드러낸 것은 무분별한 회상이 Reasoning Fixation·Belief Distortion을 유발한다는 점이고, MobilePA-Bench가 요구하는 것은 암묵적 요청 해소라는 특정 목적에 맞는 선택적 회상이다. 둘을 합치면 설계 지침이 나온다 — 회상은 기본값이 아니라 조건부여야 하며, 회상하지 않는 선택도 채점 대상이어야 한다.

평가·요건 프레임 (2026-06-25 추가)

  • Agent-Native-Memory-System (HF ↑55, 데일리 최다) — “에이전트 전용 메모리가 갖춰야 할 요건을 현재 시스템이 충족하는가”를 점검. 구현체 나열 단계를 넘어 무엇을 저장/갱신/망각할지의 평가 잣대를 제시. NatureBench·PlanBench-XL의 “에이전트를 측정하는 단계로의 이동”과 같은 맥락 — 메모리도 구현에서 평가로.

검색 사각지대 규명 (2026-07-29 추가)

  • InMind (Keep It InMind, USTC·Metastone, 125태스크) — 메모리 레이어의 **근본 실패가 저장이 아니라 검색(retrieval)**임을 규명. 직접 물으면 최대 100% 회상하나 간접 질의 적용은 14.4%(예: 알레르기 회상 후 곧바로 아몬드 마카롱 추천), 컨텍스트 직접 삽입 시 84% 성공 → “암묵적 연상 사각지대”. 이 위키·봇 메모리도 wikilink/grep “직접 매칭”엔 강해도 암묵적 연결엔 약함 — 완화책은 RARG식 관련성 랭킹 + grep 하이브리드와 능동적 연상 확장. “구현→평가” 프레임을 넘어 실패 원인의 정밀 국소화 단계.

구조 분리가 검색량을 이긴다 (2026-08-27 추가)

  • VoiceMem (HF 데일리 2위·업82·저자 10인·초록 원문 대조) — 정보 담당 좌뇌 ∥ 감정 담당 우뇌를 병렬로 두고 스트리밍 I/O를 붙인 이원 분리형. 핵심 수치는 top-5 검색으로 Mem0의 top-200보다 약 30점 높다 — 후보를 40배 적게 가져오면서 더 정확하다.
    • 함의: “많이 긁어오면 낫다”는 RAG식 직관의 반박. 설계 논점이 저장소 선택에서 무엇을 색인하고 어떻게 분리할 것인가로 이동한다. 컨텍스트와 정확도가 트레이드오프가 아닐 수 있다는 뜻이라 비용·지연이 동시에 내려간다.
    • 지연 예산 접근: 검색 134ms 가 표준 VAD 지연 안쪽이라 대화 지연이 추가되지 않는다. 절대 속도가 아니라 이미 존재하는 대기 시간 안에 숨기는 재정의.
    • 페르소나: 단·장기 정서 귀인 + 이중 노드 페르소나 모델링으로 벤치 3종 SOTA·종합 +4.29점.
    • ⚠️ 절대 점수·벤치 3종의 이름·134ms의 측정 조건(하드웨어·메모리 크기) 전량 미기재. 코드 레포 ★28로 재현 보고 부재.

MemTrapBench 반례와의 관계 — "있느냐"가 아니라 "어떻게 나눴느냐"

MemTrapBench(08-22)는 평가한 메모리 프레임워크 5종이 전부 no-memory보다 못했다(최강도 10%+ 하락)는 이 개념의 첫 정량 반례였고, 원인으로 Reasoning Fixation·Belief Distortion — 과거 기억이 현재 추론을 오염시키는 경로 — 를 지목했다. VoiceMem은 정보와 감정을 분리된 경로로 두어 감정 기억이 사실 추론에 섞이지 않게 한다. 구조적으로 오염 경로를 줄인 셈이라 두 소스가 같은 방향을 가리킨다. ⚠️ 단 “VoiceMem이 MemTrapBench를 반증했다”고 말할 수 없다 — 벤치도 태스크도 다르다. 정확한 정식화는 이것이다: 메모리의 성패는 도입 여부가 아니라 경로를 어떻게 분리했는가에 달렸다. 이 가설이 이 개념의 다음 검증 대상이다. 참고로 InMind가 규명한 실패 지점(저장이 아니라 검색)과도 층이 맞는다 — 세 소스가 각각 유해성(MemTrapBench) → 검색 실패(InMind) → 분리 설계(VoiceMem) 로 문제를 좁혀 왔다.

왜 지금 중요한가## 왜 지금 중요한가

에이전트가 단일 작업을 넘어 장기 프로젝트, 반복 태스크, 팀 협업으로 확장되면서 기억 문제가 병목으로 부상. hermes-agent 61K 스타, claude-mem 60K 스타는 모두 “AI가 기억하지 못한다”는 불만에 대한 응답.

🆕 2026-09-06 — 다섯 번째 방식 「연속 잠재 메모리」 신설 (LatentPress)

기존 넷(RAG·KV·압축·외부DB)이 기억을 어디에 어떤 형태로 두는가를 나눴고, 09-03의 Declarative-Attention 「선택적 비독해」가 읽을지 말지를 나눴다. LatentPress는 세 번째 질문을 연다 — 「어떤 형식으로 쓰는가」.

지적의 핵심은 기술이 아니라 설계 관성이다

원문: “압축된 컨텍스트는 보통 사람이 읽을 수 있는 텍스트나 디코딩해야 하는 렌더링된 이미지로 운반된다 — 그 소비자가 언어모델일 때조차도.” 요약문도 OCR 이미지도 사람을 위한 중간 형식이고, 모델은 그걸 다시 파싱한다. LatentPress는 동결된 디코더가 입력 임베딩 인터페이스로 직접 읽는 연속 메모리 토큰을 쓴다 — 추론 시 텍스트 복원 없음.

다섯 축 정리 (기억을 다루는 결정의 층위)

  1. RAG — 밖에 두고 검색한다 (판단 주체: 검색기)
  2. KV — 안에 두고 자른다 (판단 주체: 축출 정책)
  3. 압축 — 안에 두고 줄인다 (판단 주체: 요약기)
  4. 외부DB — 밖에 두고 구조화한다 (판단 주체: 스키마)
  5. 선택적 비독해(Declarative-Attention) — 두되 안 읽는다 (판단 주체: 모델 자신)
  6. 🆕 연속 잠재 메모리(LatentPress) — 모델의 모국어로 쓴다 (판단 주체: 학습된 writer 어댑터)

수치: LongMemEval 0.504 @ 7.70배 압축 vs 무압축 원문 0.490 — 압축본이 원문을 이겼다. 텍스트 요약 0.184 · OCR 0.4260.312 대비 큰 격차. 어댑터만 학습(4.2M~26.2M · 디코더의 ~0.1%), 쓰기 43ms/대화, 읽기 59배.

⚠️ 이 축의 고유 비용 — reader-matched 결박

어댑터가 특정 디코더에 맞춰 학습된다. 즉 모델을 바꾸면 메모리 자산을 다시 만들어야 한다. 1~4축은 모델 교체에 비교적 중립적이었으나 이 축은 아니다. 같은 배치의 HarnessDev가 하네스 개선의 모델 간 전이가 제한적임을 독립적으로 보고했다 — “외부에 두었지만 실제로는 특정 모델에 결박된다”는 같은 형태의 함정이 메모리 층과 하네스 층에서 동시에 관측됐다. 이 배치의 교차 발견.

축들 사이의 미해결 충돌

Random-Attention은 KV 축출에서 선택 신호의 기여가 거의 0이라 했고, LatentPress는 잠재 압축이 원문을 이긴다(=선택/정제가 이득)고 한다. 대상이 달라 직접 모순은 아니나(축출 vs 쓰기), “기억에서 선택이 얼마나 중요한가”에 대해 반대 방향을 가리킨다. 대조 관측 대상으로 고정.

🆕 2026-09-24 — 같은 날 두 논문이 메모리를 서로 다른 모달리티에서 재정의했다

① SpeakerMem-R1 (대화) — 실패는 검색이 아니라 귀속이다

초록이 두 병목을 명명한다: “message attribution and relational understanding in multi-party dialogue, and state reconstruction from interleaved histories”. 🎯 이 페이지의 기존 축(mem0·VoiceMem)은 무엇을 저장·검색하는가 였다. 다자 대화에서는 내용이 남아도 화자를 잃으면 쓸 수 없다.

  • 이중 트랙: 화자 라벨 붙은 원문 + 파생 상태(person-level / group-level 2뷰), 질의 시 엔티티·사건·시간으로 결합
  • 수치(절대 정확도): GroupMemBench 47.9 · SocialMemBench 69.2 · EverMemBench 61.9 · LoCoMo 1,986문항 70.85 · 통제 305문항 SFT 57.38 → RL 68.20
  • 🔴 GroupMemBench 47.9% = 절반 이하. SOTA 주장과 무관하게 다자 대화 메모리는 아직 대체로 실패한다.

② The-Past-Frames-the-Future (영상 생성) — 조작적 정의

“persistent historical information maintained across outer AR steps, capable of influencing future generation even after the originating evidence is no longer locally accessible” 🎯 긴 컨텍스트를 넣은 것은 메모리가 아니다. 증거가 사라진 뒤에도 남는 것만 메모리다. 이 페이지가 그동안 느슨하게 써 온 “메모리”에 반증 가능한 경계가 생겼다.

  • Operations 5단(쓰기·읽기·갱신·관리·통합)은 이 페이지의 하위 구조로 그대로 채용 가능
  • 문제의 위치를 정확히 짚는다: “critical historical information … often leaves the active context long before its relevance diminishes” → 용량 문제가 아니라 퇴출 시점과 관련성 감쇠의 불일치

🎯 두 논문의 교차 — 메모리 문제가 모달리티를 넘어 같은 모양이다

  • 대화: 누가 말했는지를 잃는다 → 화자 라벨을 원문과 함께 보존
  • 영상: 누가/무엇이 있었는지를 잃는다 → entity identities 를 1급 보존 대상으로 명명 둘 다 “요약하면 정체가 사라진다” 고 말한다. 압축이 아니라 이중화(원문 트랙 유지)가 공통 처방이다. 📌 ChinameBot 적용 경로: GRPO 학습 없이 이중트랙 저장 + 질의시 결합만 베끼는 것이 가능하다. 저장 구조 변경만으로 모델 교체 불필요. 🔴 대가: 원문 보존 → 저장량 증가 + 질의 시 결합 비용. ⬜ 두 논문 모두 그 수치를 초록에 안 적었다.

2026-09-26 갱신 — 보존 처방과 편집 처방이 정면으로 갈렸다

같은 주에 이 축의 반대 극 두 개가 도착했다.

  • 보존(이중화): SpeakerMem-R1(대화) · The-Past-Frames-the-Future(영상) — 09-24 관측 “압축이 아니라 이중화, 원문 트랙 보존”
  • 편집(수정): AEWM(09-26) — “task-state contamination: unsupported assumptions and outdated plans persist in history and distort subsequent decisions” → State Revision 이 히스토리를 직접 고쳐 쓴다

🎯 같은 현상(히스토리가 쌓인다)에 정반대 처방이 나왔다

보존파는 “요약이 원문을 죽이니 원문을 남겨라”, 편집파는 “낡은 것이 남아 결정을 오염시키니 지워라”. 둘 다 옳을 수 있고, 갈림길은 “무엇이 낡는가”다 — 사실(fact)은 보존하고 계획(plan)은 편집하는 것이 합의점으로 보이나 ⬜ 어느 논문도 이 구분을 명시하지 않는다. 🔴 AEWM 의 미해결 실패 모드: 오편집이 누적되면 되돌릴 근거 자체가 사라진다(초록 미언급).

제품 구현체가 붙었다 — hindsight

2층 승격 구조(memory bank 원자 관찰 → mental model 성향 요약) + retain / recall / reflect 3연산. Python 임베디드 모드(서버 불필요) 와 MCP 서버 경로. 🎯 mem0(★65,688, 사실상 기준점)에 이은 두 번째 대형 오픈코어(★30,382)이고, 오픈/폐쇄의 절단면이 다르다 — mem0는 평가 하네스를 열고 피측정물을 닫았고, hindsight는 누가 쟀는지를 열고 점수를 닫았다(벤치마크-이미지-봉인). 🔴 따라서 이 축에서 지금 비교 가능한 정량 수치는 여전히 없다. LongMemEval 이 공통 자로 등장했으나(hindsight 주장) 값이 PNG 안이다 → actionable: arXiv 2512.12818 본문에서 문자 수치 확보.
