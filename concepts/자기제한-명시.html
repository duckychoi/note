자기제한 명시

🏆 2026-10-03 새 축 — 정직성은 문서 단위가 아니라 "매체 단위"로 갈린다

HC-DLM 이 결정적 사례다. 본문은 자기 패배를 수치까지 적어 명시한다: “the matched CCDD implementation attains comparable and marginally higher accuracy (94.65 vs. 94.21)”. 초록은 같은 결과를 “improves … in puzzle accuracy on Sudoku and Countdown” 으로 뭉갠다. ⇒ ⚖️ 같은 저자가 같은 날 같은 논문에서 한쪽은 실행하고 한쪽은 실행하지 않았다. 📌 그래서 “이 저자는 정직하다/과장한다”는 판정 단위가 틀렸다 — 판정 단위는 매체다(초록 / 본문 / README / 모델카드 / 트렌딩 요약). 🎯 10-02 결론 “신뢰도는 벤더 단위가 아니라 소스 단위로 매긴다” 의 한 단계 아래로 내려간 조항: 같은 소스 안에서도 매체별로 매긴다.

✅ 같은 배치 자발 공개 3건 ① On-Policy-or-Off-Policy-Distillation — 견고성 범위 명시형(신규 변종). “Our broader conclusions remain robust to removing gradient clipping, using sampled KL estimators, and training on tasks requiring longer reasoning chains.” ⇒ 3가지 교란 조건을 스스로 열거한다. 📌 종전 변종들은 “언제 안 되는지” 를 적었고, 이것은 “어디까지 흔들어도 되는지” 를 적는다 — 반증 조건의 사전 제시다. 🔴 단 “유지된다”는 서술이고 수치가 아니다. ② HC-DLM 본문 — 패배 수치 명시 + “best generative perplexity among the evaluated diffusion models” 로 자기회귀에 지는 것을 한정어로 정확히 처리(AR Transformer 66.7 < HC-DLM 75.5) + 파라미터 정의 명시(샘플링 시점 생성 파라미터, 토큰 임베딩 제외). ③ Sharpening-Tax — 자기 발견을 “surprising” 이라 적는다 + “even task-specific RL tuning on a single domain pays Sharpening Tax” 로 자기 지표가 자기 처방에도 적용됨을 추가 확인. 🏆 ④ 벤더 쪽 — ponytail 이 CONTRIBUTING.md 에 “benchmark gate for ruleset changes” 를 넣었다: 자기 룰셋 변경에 벤치마크 통과를 요구하는 자발적 장치. 🎯 10-02 에 이 레포가 자기 수치를 하향 정정(“80~94%” → “과제별 상한”)한 것과 같은 궤적이다 — 이 레포는 자기 주장을 스스로 조이는 방향으로 움직인다. 🔴 그리고 10-02 경고를 반복한다: 정직성은 성능의 증거가 아니다. HC-DLM 은 정직하게 적고도 Sudoku Easy 를 졌다.

✅ 같은 날 볼트 자신의 사례 — 3개월 전 경고가 확증됐다. caveman 페이지는 2026-07-03 에 “README 는 ~75% 를 주장” + ⚠️ “외부 요약에서는 약 65%로 전해짐 — 수치 자체가 소스마다 엇갈림” 이라 적었다. 오늘 수집기가 전한 자기 주장이 65% 다. ⇒ 📌 자가 제출 수치는 시간이 지나면 내려간다. 볼트가 “엇갈림”을 적어 둔 것이 3개월 뒤 확증으로 바뀌었다 → 측정도구-먼저-반증.

2026-09-18 — 🎯 같은 날 배달된 두 문서의 인식론적 품질이 정반대였다. 그리고 "벤치 0개"를 두 종류로 갈랐다

✅ 최상위 형태 — opensre(★11,124): 저자가 적었다 “AI SRE, and AI for production debugging more broadly, remains unsolved”. 🎯 기능의 한계가 아니라 분야 전체의 미해결성을 선언했다. 그리고 이 선언이 벤치마크 부재를 설명한다 — 수치가 없는 게 누락이 아니라 재는 자가 아직 없다는 진술이다. ✅ 논문 채널 최강 — When-EOS-Tokens-Disagree: 원인 하나를 특정한 논문이 “important, but not exhaustive” 를 초록에 적고, 정지집합 정렬만으로는 “insufficient” 라고 밝혔다. 자기 기여에 스스로 상한을 걸었다. 🔴 반대 극 — harness-sdk(★7,345): “Guardrails catch mistakes before they run” 을 측정 없이 단언했다(155행 README에 벤치 섹션 자체가 없음). 그리고 카드 설명 “any model, any cloud” 와 기본 프로바이더가 Amazon Bedrock이라는 성립 조건이 같은 문서에 있다.

📌 볼트 규칙 신설 — “벤치 0개”는 두 종류다

주장 있음 + 근거 없음   → reliability 하락   (harness-sdk · [[MiroFish]])
주장 없음 + 근거 없음   → 근거 등급 문제 아님, 성숙도 문제  (opensre · [[mms-300m]])

🎯 지금까지 볼트는 “벤치 0개”를 일률적으로 감점해 왔다. 그건 틀렸다 — opensre·mms-300m 은 벤치가 0인데 reliability high 다. 주장하지 않은 것에 근거를 요구할 수 없다.

한 줄

자기가 하지 않는 것을 먼저 밝히는 문서가, 하는 것만 밝히는 문서보다 신뢰할 만하다. 그리고 이건 취향이 아니라 측정 가능한 품질 신호다 — 한계를 쓰려면 한계를 알아야 하고, 한계를 알려면 실제로 써봤어야 한다.

2026-09-10 배치의 4개 사례 — 서로 다른 층위에서 같은 습관

① 스킬이 능력에 상한을 건다 — Pascal-Editor 의 furniture-fit 카드가 하지 않는 것을 먼저 못박는다: “높이·개폐·배송 검증을 주장하지 않는, 경계가 명시된 근거 기반 설치면적 평가”. 더 중요한 건 런타임 규약이다 — 스킬이 MCP 툴 스키마를 먼저 조회해 옵션 필드 유무를 확인하고, 없으면 더 좁은 결과를 보고한다. → “레포에 기능이 있어도 설치된 릴리스에는 없을 수 있다”를 전제한 설계. 대부분의 스킬은 상류 최신 상태를 가정하고 조용히 깨진다.

② 격리 주장에 상한을 명시 — PI-Desktop

“플러그인 프로세스는 권한 게이트되고 렌더러와 격리되지만, 완전한 OS 샌드박스가 아니라 사용자가 신뢰하는 코드다.” → 격리를 주장하면서 그 격리의 한계를 같은 문장에서 밝힌다. 대부분의 하네스는 “샌드박스”를 검증 없이 쓴다.

③ 트레이드오프를 먼저 공개 — Qwopus3.8-27B-Flash-GGUF 카드 본문: “추론 효율을 개선하는 대신 MMLU-Pro 점수가 낮아지는 명시적 트레이드오프” · “아래 처리량 결과는 속도를 측정한 것이지 정답 정확도가 아니다”. 나아가 자기 수치의 등급을 구분한다 — SWE 배터리 13/14는 “엄격한 단일 실행” 이고 베이스 비교값이 — 라 비교 주장 불가, “처리량 ~8% 향상”은 “별개의 근사 측정”. 알려진 결함도 자인 — 일부 Python 과제에서 잘못된 들여쓰기 생성.

④ 설치 함정을 README가 직접 경고 — text-to-cad “npx skills update 는 락파일에 있는 것만 갱신해 신규 스킬을 조용히 누락한다” · “두 명령 모두 상류에서 폐기된 스킬을 제거하지 않는다” · “구버전 Codex는 플러그인을 조용히 건너뛴다”. → 세 실패가 전부 조용하다. 이걸 문서에 쓴다는 건 사용자가 당한 뒤 이슈를 올렸다는 뜻이기도 하다.

왜 이것이 신뢰 신호인가

볼트가 반복 관찰한 반대 패턴은 “벤더의 자기규정 vs 벤더의 자기측정” 이었다 — 09-09 GLM-5.3-CYBERSECURITY-FP8 에서 카드의 포지셔닝 문장을 같은 카드의 벤치마크 표가 반박했다. 규정이 측정보다 관대한 경우다. 자기제한 명시는 정반대 — 규정이 측정보다 보수적이다. → 판별식: 문서가 자기에게 유리한 방향으로 틀렸는가, 불리한 방향으로 틀렸는가. 불리한 방향으로 틀린 문서는 나머지 주장도 검증했을 가능성이 높다.

이 신호를 과신하면 안 되는 경우

한계를 명시했다고 명시하지 않은 한계가 없는 건 아니다.

  • PI-Desktop 은 샌드박스 한계를 밝혔지만 Early Preview 자인 + 생성일 2023-03-22인데 당일 +417 스타라는 불일치는 볼트가 따로 지적해야 했다(레포 나이가 성숙도를 과대표시).
  • Qwopus3.8-27B-Flash-GGUF 는 트레이드오프를 정직하게 공개했지만 비전 성능 측정이 아예 없다 — 멀티모달 모델인데 벤치마크가 전부 텍스트다. → 정직한 문서에서도 “언급되지 않은 축”이 가장 위험하다.

내 스킬·문서 규약에 이식할 것

  1. 스킬 카드에 “하지 않는 것” 절 추가 — 지금 내 스킬들은 할 수 있는 것만 쓴다.
  2. 런타임 능력 확인 — furniture-fit 방식으로 툴 스키마를 먼저 조회하고 없으면 좁은 결과를 보고. 지금 내 스킬은 툴이 없으면 조용히 틀린 답을 낸다.
  3. 수치 등급 표기 — 단일 실행 / 비교 가능 / 근사 측정을 구분해 적는다.
  4. 의존성 핀 고정 — text-to-cad 의 requirements.txt 릴리스 고정 방식.

🔄 2026-09-11 갱신 — colibri: 개런티를 어디에 걸지 스스로 고른다

성능이 아니라 의미론에 개런티를 건 사례

colibri(⭐27,617·Apache-2.0·C) README 35~38행 원문:

“there is no SLA on speed, and a hard guarantee on semantics: … [no experiment] silently changes model precision or router semantics” → 🎯 속도 주장을 포기하고 “조용히 바꾸지 않는다”를 판다. 744B를 소비자 하드웨어에서 돌리는 저장소가 속도를 팔지 않는 것은 반직관적이고, 그래서 신뢰 신호다. → 그리고 실측 하한까지 공개한다: 6×RTX 5090에서 5.8~6.8 tok/s(TTFT ~13s) / 25GB 박스에서 0.05~0.1 tok/s(콜드) — “the proven floor”. → 가장 나쁜 수치를 자기가 먼저 적는다. pascalorg 의 furniture-fit(툴 스키마 선조회 후 없으면 좁은 결과 보고)와 같은 계열.

🆕 이 사례가 추가하는 것 — 개런티를 검증 가능한 형태로 냈다

자기제한 명시의 약점은 “안 바꾼다”는 말을 어떻게 믿나 였다. colibri의 답:

  • CUDA VRAM 전문가 계층 on/off에서 출력이 비트 단위 동일(README 414·437행: “output bit-identical to the CPU path”)
  • 미러 SSD는 시작 시 검증(파일 크기 + safetensors 헤더 바이트 동일), 불일치 시 조용히 주 디스크 폴백(231행) → 🎯 자기제한을 주장이 아니라 테스트로 환원했다. 이것이 이 개념의 성숙 형태다: “우리는 X를 하지 않습니다” → “X를 하지 않았음을 이렇게 확인할 수 있습니다.” → 검사가능성-공사 와 정확히 접속한다 — 비트 동일성은 외부 정답 고정의 한 형태(정답 = 기준 경로의 출력).

반대 사례가 같은 배치에 있다

Clodds 는 README 상단에 자체 토큰 컨트랙트 주소를 두고 성능·수익을 서술한다. 자기제한이 아니라 자기이익 명시다. → 두 저장소를 나란히 놓으면 판정 기준이 선명해진다: 저자가 자기 주장의 한계를 먼저 적는가, 자기 이익을 먼저 적는가.

🆕 2026-09-17 — 최강 사례: 자기 증거 기준을 자기 주장에 재귀 적용 (oh-my-hermes)

🎯 벤치마크 칸에 "아직 측정 안 했다"를 적었다

oh-my-hermes README 604행은 A/B 벤치 레인을 정의한다(자기 레포의 머지된 PR을 코퍼스로, 그 PR의 테스트로 채점, 4지표: pass rate · cost per passed task · wall clock per goal · false-completion rate). 그 다음 줄 — 볼트 문자 일치:

“No measured run has been published yet. The lane, its corpus, and its offline pilot are in place; this section carries the table once a run exists whose records the repository can point at.”

🎯 섹션을 지우지도, 미검증 수치로 채우지도 않았다. 남겨 두고 빈 상태를 명시했다. 📌 그리고 이것은 자기 도구의 어휘를 자기에게 적용한 것이다 — 같은 README가 정의한 4상태(Plan · not run / Code · running / Code · reported done / Test · verified) 중 자기 벤치마크를 Plan · not run 에 둔 셈이다. 🔴 볼트가 지금까지 본 이 개념의 사례 중 가장 강하다: earendil-works(경계·무모순·대안 3칸)는 제품의 한계를 적었고, vxcontrol은 경계를 적으면서 헤드라인은 고치지 않았다. 이쪽은 기준 자체를 재귀 적용했다.

🎯 도구가 자기 실행 조건의 실패 모드를 미리 적었다 ( security-audit-skill)

같은 배치 Cloudflare 스킬 README 90행 — 볼트 문자 일치:

“An OS-enforced sandbox for target-controlled builds… Without these controls, the workflow keeps the lead as needs_validation instead of executing target code.”

🎯 조건 미달 시 무엇을 하는지 미리 선언했다 — 조용히 낮은 신뢰도로 진행하지 않고 확인을 포기하고 미해결로 남긴다. 📌 성능 수치보다 이것이 검증가능성에 대해 더 많이 말한다: 수치는 성능의 약속이고, 이 조항은 실패 모드의 약속이다.
