🔴🔴 2026-10-04 볼트가 어제 요청한 "관측 시각 병기"를 어제 기록이 안 지켰다 — 그래서 오늘 일증분을 확정할 수 없다

10-03 에 볼트는 수집기에게 “관측 시각 병기” 를 요청했다. 🔴 그런데 10-03 볼트 기록 자체에 관측 시각이 없다(ponytail ★152,194 · impeccable ★74,563 · caveman ★109,249 · Agent-Reach ★89,190 전부 시각 미기재 · 10-02 ★151,003 도 없다). ⇒ 🔴 결과: 오늘 24시간 증분을 계산할 수 없다. 산술은 가능하지만 구간 길이를 모른다. ⚖️ 따라서 “일평균”으로 적지 않고 “구간 미확정 증분”으로만 적는다. 🏆 요청의 필요성이 하루 만에 자기 기록에서 증명됐다. ✅ 오늘부터 UTC+KST 병기(오늘 관측 2026-10-04T09:12:13Z / 18:12 KST). 🎯 시각이 필요한 이유의 구체 사례도 나왔다 — impeccable pushed 가 2026-10-04T09:04:31Z 로 볼트 관측(09:12:13Z)보다 8분 앞이다. 시각 없이는 이 사실을 표현할 수 없다.

⚖️ “stars today” 편향의 방향이 뒤집혔다 — 10-03 결론을 좁힌다

10-03 기록: 트렌딩 “+1,435 stars today” ↔ API 24h +1,191 ⇒ “트렌딩이 +20~21% 과대” · 지표-창길이 에 “GitHub 자체 지표 간 불일치” 로 등재. 10-04 전수 비교(수집기 “당일” ↔ 볼트 구간 증분):

🆕 30일 창이 성장을 6배 과소평가한다 — 정량 사례

LTX-2.5 09-30→10-04(4일): 30일창 +40,886 ↔ 누적 +252,171. ⇒ 차이 211,285 가 창 밖으로 빠졌다. 📌 창 증분으로 성장률을 재면 실제의 약 16% 로 보인다. ⚖️ 나이 73일 모델에서 30일 창은 성장 측정에 부적합하다 — 누적 차분을 쓴다. ✅ 반대 극 확인: Ternary-Bonsai-2-27B 는 나이 18일 < 30일 이므로 downloads(30일) == downloadsAllTime == 3,969,867 이 정상이다(10-01 규칙의 8번째 실례).

🆕 활동의 버스트성 — 한 주기가 관측됐다

10-03 에 ponytail 에서 “방치 18일이 아니라 18일 침묵 → 하루 15커밋 배치 릴리스” 로 재해석하며 이 축을 세웠다. ✅ 10-04 pushed 가 어제와 동일 = 오늘 푸시 0 ⇒ 침묵 → 버스트 → 침묵이 한 주기 관측됐다(n=1 주기). 📌 계속 볼 값은 pushed 자체가 아니라 버스트 간 간격이다. 🎯 대조군 3일째 유지: Agent-Reach pushed 2026-09-15T16:16:24Z = 19일 동결(10-03 “18일”의 +1). 같은 라벨의 두 레포가 갈린 상태가 n=3일째다.

✅ 2026-10-03 7번째 실례 — 처음으로 규칙이 먼저 있고 관측이 뒤에 왔다

Qwen3.8-27B 30일 DL: 수집기 6,934,867 → 볼트 실측 6,895,117 = −39,750 (−0.57%). ✅ createdAt 2026-08-05 → 나이 59일 > 30일 ⇒ 30일 창에서 과거 일자가 빠져나가므로 감소가 구조적으로 가능하다. 📌 10-01 에 명문화한 규칙이 예측한 그대로다. 종전 6회는 관측이 먼저였고 설명이 뒤였다. 이번엔 규칙으로 먼저 예상하고 확인했다 ⇒ ⚖️ 이 개념이 사후 설명에서 사전 예측으로 넘어간 첫 사례다.

🆕 새 축 — 값이 엔드포인트/파라미터에 의존한다 trendingScore 는 기본 조회에 나타나지 않고 ?expand[]=trendingScore 에서만 나온다(기본 None → expand 352 = 수집기 수치와 일치). ⇒ 🔴 10-02 의 “trendingScore 는 감쇠한다(3/3 하락: 774→771·418→416·280→279)” 관측은 기각되지 않는다 — 수집기가 expand 경로로 읽었다면 유효하다. 그러나 그 관측을 기본 조회로 재검증하려 했다면 “필드 소멸”로 오판했을 것이다. ⚖️ 조항 추가: 지표를 시계열로 쌓을 때 “어떤 요청으로 얻은 값인지”를 함께 적는다. 요청이 다르면 같은 이름의 지표가 다른 값(또는 None)이다 → 무응답-오귀속 요청 미지정형(오늘 신설) · 암묵을-명시로.

🆕 새 수치 축 — 창 비중: 누적 12,626,437 vs 30일 6,895,117 = 54.6%. 나이 59일 중 30일이 생애 다운로드의 절반 이상을 차지한다. 📌 lastModified 가 50일째 동결인데 수요는 가속 중이다 — 같은 배치 Agent-Reach(18일 동결 · ★일평균 393) 과 같은 패턴이 모델 쪽에서도 관측된다.

🔴 미해소 관측 1건 — 같은 축에서 베이스와 파생이 다르게 움직였다. 같은 창에서 베이스 Qwen3.8-27B 는 −39,750 감소, 파생 Qwen3.8-27B-GGUF 는 드리프트 0. 둘 다 30일 초과(59일 / 51일)이므로 나이만으로 설명되지 않는다. ⚖️ 판정 보류 — n=2 이고 일별 분포를 모른다. 🔴 “드리프트 0 = 검증 통과” 로 읽지 않는다(10-01·10-02 에 두 번 깨진 논리다). 📌 감소가 구조적으로 가능한 나이인데 0 이라는 것은 설명이 필요한 관측이지, 안정성의 증거가 아니다.

🆕 GitHub 자체 지표 간 불일치 — 유형 확정(2배치 연속 미해소) ponytail 트렌딩 “+1,435 stars today” ↔ 24시간 API 실차 +1,182~1,191 = 차이 약 244253(+2021%). fork 도 같은 창에서 +63. 🔴 원인 미확인 — stars today 의 창 정의(UTC 00:00 / 롤링 24h)를 모르므로 어느 쪽이 틀렸다고 적지 않는다. 📌 종전 사례는 전부 수집기↔볼트 시점 차였고, 이것은 같은 제공자의 두 지표 간 불일치다.

🆕 pushed 의 버스트성 — 활동량이 아니라 릴리스 리듬이다 ponytail: 10-02 에 볼트가 “18일째 동결 확증” 으로 적은 필드가 10-03 에 갱신됐는데, 커밋 로그 실측 결과 하루에 15커밋 + 릴리스 v4.10.3 이었다. ⇒ ⚖️ “18일 방치”가 아니라 “18일 침묵 → 하루 배치 릴리스”다. 단일 시점 pushed 로 유지보수 상태를 판정할 수 없다. 🎯 같은 배치 Agent-Reach 가 18일 동결을 유지해 대조군이 됐다 — 같은 라벨의 두 레포가 하루에 갈렸다.

🔴 먼저 — 이 페이지는 "새 발견"이 아니다. 볼트는 이미 알고 있었다

수집기는 이번 배치에서 ”🔴 이번 배치 최대 발견 — DL 수치의 의미가 바뀐다” 며 30일 창 가설을 제시했다. ✅ 볼트 실측 반박: 볼트는 이 사실을 최소 2026-09-06부터 관측했고 09-15에 규칙으로 명문화했다.

  • HuggingFace 엔티티 27행: ”🔴 downloads 는 30일 누적이다 — 전체 누적이 아니다” · 32행: “다운로드는 ‘30일’을 항상 병기한다”
  • MiniMax-H3-Physical-Reasoning 71행: 09-06 4,986,349 → 09-19 4,449,605, “줄었다(누적 아님)” 로 이미 정확히 해석
  • Qwen3.6-35B-Uncensored 17행: “30일 롤링 윈도 기반이라 신규 유입 둔화 시 수치가 감소하는 정상 등락” 🎯 그러므로 “볼트의 증분 해석 전체를 재검토해야 한다”는 수집기 주장은 과장이다. 볼트는 감소를 이미 창 이동으로 읽고 있었다.

✅ 내부 정합 검증 — 가장 어린 레포가 증명한다

Ternary-Bonsai-2-27B 는 2026-09-16 생성 = 7일 차, 창 길이보다 어리다. 이 레포만 두 값이 정확히 일치한다(2,569,604). 성숙한 레포 2건은 벌어진다(7.08M<9.68M · 7.02M<13.99M). 🎯 레포 나이 < 창 길이면 두 값은 같아야 한다 — 3표본이 이 예측을 정확히 만족. 창 해석과 누적 필드 양쪽이 동시에 확인됐다.

수집기 판정: “Qwen3.8-27B ↔ Qwen3.8-27B-GGUF 격차 0.85% → 역전 성립 안 함. 반례 1건 추가.”

  • 누적: 9,681,199 vs 13,993,047 → 파생이 원본의 1.445배, 역전 성립 🔴 반례가 아니라 지지 사례였다. 새로 열린 누적 축이 없었다면 오염된 반례가 개념 페이지에 들어갔다 → 측정도구-먼저-반증.

🔴 볼트 자기 한계 (숨기지 않는다)

규칙은 있었는데 적용되지 않았다

HuggingFace 32행의 “다운로드는 ‘30일’을 항상 병기한다” 는 09-15에 만든 볼트 자체 규칙이다. 그런데 09-22 log.md 는 여전히 4,511,348→4,960,483(+449,135) 형태의 맨 증분으로 적었다(233행). 창 표기 없음. 🎯 지식이 페이지에 있는 것과 규칙이 작업에 적용되는 것은 다르다 → 암묵을-명시로 의 역방향 사례: 명시했는데도 적용되지 않았다. 📌 그래서 수집기가 “발견”으로 되가져왔을 때 볼트가 바로 반박하지 못할 뻔했다. 자기 규칙의 미적용이 남의 과장을 키운다.

⬜ 확인 범위 (부재 주장에 범위를 붙인다)

  • 창 길이가 정확히 30일이라는 건 ⬜ 공식 문서로 확인되지 않았다. huggingface/hub-docs docs/hub/models-download-stats.md 전문 3,934바이트 확인 — 카운팅 방식(쿼리 파일·GGUF·diffusers)만 서술하고 기간은 한 글자도 없다. “30일”은 볼트·커뮤니티의 관측 기반 통용값이다.
  • 기존 원본-파생-역전 사례 6건의 누적값 재조회 미수행 → 역전 방향이 바뀌는 사례가 더 있을 수 있다.

볼트 규칙 (개정)

  1. HF 모델 조회는 ?expand[]=downloadsAllTime 필수. 두 값을 항상 병기: DL 7,079,646(30일) / 9,681,199(누적).
  2. A→B 증분 서술은 누적값에서만. 30일 값의 차이는 “창 이동” 으로 적는다.
  3. 동결·감소는 이제 “관측 실패”로 남기지 않는다 — 누적 축으로 교차 확인한다. (기존 Qwen3.8-27B 109행의 “격일 갱신 가설” 도 누적 축으로 재검토 가능해졌다)
  4. 창 길이는 ⬜ 문서 미확인 상태로 표기한다. “30일”을 단정하지 않는다.

🆕 2026-09-24 — 창 길이에 처음으로 수치 근거가 붙었다 (문서는 여전히 없다)

🔴 이 추정이 기대는 가정 — 숨기지 않는다

균일 다운로드율 가정이 계산의 전부를 떠받친다. 실제 모델 다운로드는 보통 출시 직후 몰리고 감쇠한다.

  • 감쇠한다면 → 최근 30일 몫이 비례보다 작아야 한다 → 관측값(15.02% > 비례 14.35%)은 최근 유입이 평균보다 많다는 뜻 → 함의 창은 30일보다 짧아질 여지
  • 즉 28.5~31.4일은 신뢰구간이 아니다. 두 개의 점추정이고, 각각 해당 저장소의 다운로드 곡선 모양에 오염돼 있다. 🔴 여전히 ⬜ 미확정이다. 다만 등급이 달라졌다: “근거 없음” → “실측 2건이 30일 근방과 정합, 문서 미확인”. ⬜ 추가로 필요한 것: 같은 저장소를 며칠 간격으로 연속 관측해 창이 어떻게 미끄러지는지 직접 보는 것. 1회 스냅샷 역산보다 강하다 → actionable.

createdAt 나이 30일 초과는 두 값 불일치의 필요조건이지 충분조건이 아니다. 판정 기준은 나이가 아니라 “창 밖 구간에 실제 다운로드가 있었는지” 이고, 그것을 가르는 것은 createdAt 이 아니라 공개일(Release Date · 카드 기재) 이다. 🎯 이로써 이 개념의 변수가 3개로 분해됐다: createdAt(레포 생성) · Release Date(실제 공개) · 조회 시점. 10-01 까지 볼트는 첫째와 셋째만 보고 있었다. 📌 즉 레포 생성과 공개 사이의 잠복 기간이 세 번째 변수였고, 그것이 없다고 암묵 가정하고 있었다 → 암묵을-명시로.
