캐시된 지표 신선도

🏆🏆 2026-10-04 결정적 시험 통과 — 동결은 레코드 단위가 아니라 필드 단위다

Qwen3.8-27B 가 이 개념의 직접 시험 사례로 들어왔다. 볼트 실측 3회차 비교(전부 expand[] 조회):

필드09-3010-0310-0424h
downloads (30일)7,020,2396,895,1176,895,117🔴 0
downloadsAllTime11,744,21512,626,43712,626,437🔴 0
likes16,59016,82516,898✅ +73
trendingScore—352348✅ −4
🏆 같은 HTTP 응답 안에서 likes 와 trendingScore 는 움직이고 다운로드 두 필드만 멈췄다. ⇒ ⚖️ 레코드가 캐시에서 나온 것이 아니다. 동결은 응답의 속성이 아니라 다운로드 집계 파이프라인의 속성이다. 📌 이것이 “캐시된 지표”를 레코드 단위로 의심해 온 종전 프레임을 필드 단위로 좁힌다.

🔴 그리고 그 동결은 자기모순이다 — 단조 카운터가 0 증가했다

downloadsAllTime 은 누적 단조 카운터다. 감소할 수 없고 수요가 있는 동안 정지할 수도 없다. 기대 증분을 볼트 자기 데이터로 계산한다: 09-30 11,744,215 → 10-03 12,626,437 = +882,222 / 3일 = 일평균 ≈294,074. 30일 창 6,895,117 / 30 ≈ 229,837/일 도 같은 자릿수다. ⇒ 🔴 24시간에 23만~29만이 더해져야 하는데 0 이 더해졌다. 0 은 측정값이 아니라 결측이다.

🆕 볼트 규약 (2026-10-04 발효)

  1. 누적 단조 지표가 전일과 완전히 동일하면 “변화 없음”이 아니라 「집계 결측」으로 분류한다.
  2. 판정 근거 2개를 함께 적는다: ⓐ 같은 응답의 다른 필드가 움직였는가(움직였으면 레코드 캐시가 아니다) ⓑ 직전 구간의 일평균이 0 과 양립하는가(양립 불가면 결측이다).
  3. 🔴 “수집기–볼트 드리프트 0” 을 정확성의 증거로 쓰지 않는다. 양쪽이 같은 결측값을 읽었을 수 있다.
  4. ✅ 관측 시각을 UTC+KST 로 병기한다 — 필드별 신선도를 말하려면 시각이 필요하다.

🔴 소급 영향(actionable): 볼트는 과거에 다운로드 완전 일치를 “양측 정확” 의 증거로 기록한 적이 있다(09-30 LTX-2.5 “드리프트 0” 등). ⚖️ 그 해석은 규약 3항에 의해 무효화될 수 있다 — 재검토 대상이다. 📌 같은 배치 대조군: LTX-2.5 와 Ternary-Bonsai-2-27B 는 두 다운로드 필드가 정상 갱신됐다(각 +252,171 / +512,743). ⇒ 🎯 결측은 HF 전역이 아니라 특정 레포(또는 특정 샤드)에서 발생했다.

🎯 핵심 — 한 플랫폼이 다른 플랫폼의 지표를 중계할 때, 그 값은 관측이 아니라 사본이다

2026-09-27 배치에서 확정된 사실: HuggingFace papers API 의 githubStars 는 실시간 조회가 아니라 지연된 캐시값이다.

볼트 3점 실측 (WROP-Object-Permanence 부속 hokindeng/object-permanence, arXiv 2609.28654):

  • 09-26 HF API githubStars = 12 ← 볼트가 이 값을 페이지에 기록
  • 09-27 HF API githubStars = 91
  • 09-27 GitHub API 직접 조회 = ★121

🎯 즉 같은 시각에 두 출처가 91 과 121 을 말한다(+30 차이). 어느 쪽도 틀리지 않았다 — HF 는 자기가 마지막으로 가져온 값을 정확히 보고하고 GitHub 은 현재 값을 정확히 보고한다. 틀린 것은 둘을 같은 것으로 취급한 독자다.

🔴 이것이 볼트에 직접 손해를 냈다

볼트 WROP-Object-Permanence 페이지 46행에 “githubRepo hokindeng/object-permanence ★12, HF API 실측” 이라 적혀 있다. “실측”이라고 적었다. 🔴 실제로는 HF 의 캐시를 읽은 것이고, 그날 GitHub 실제값은 12보다 컸을 가능성이 높다(하루 뒤 캐시가 91 이 됐으므로). 📌 표기 규약 위반이다: 볼트는 “실측” 을 볼트가 직접 조회한 값의 뜻으로 써 왔는데, 이 경우 중계된 값을 직접 조회한 것이다. 조회 행위는 직접이고 값은 간접이다. → 규약 신설: 중계 출처의 값은 X(출처 캐시) 로 적고, 원 출처를 직접 조회한 값만 실측 으로 적는다.

🎯 어긋난 것은 급상승 중인 1건뿐이다 — 이것이 법칙을 준다

09-27 배치 부속 GitHub 5건 대조:

  • object-permanence — HF 91 vs GitHub 121 → 어긋남(+30)
  • OmniEcho ★12 · AEWM ★6 · pos-sae-latents ★0 · robocode ★13 → HF 와 GitHub 실측 일치 🎯 즉 캐시 지연은 상수인데 오차는 상수가 아니다. 오차 = 지연 × 변화 속도다. 정체된 레포는 캐시가 며칠 낡아도 값이 같고, 급상승 레포만 벌어진다. 📌 역설적 귀결: 캐시값은 중요하지 않은 것에 대해서는 정확하고 중요한 것에 대해서만 틀린다. ★0~13 짜리 레포 4건에서는 문제가 없었고, 유일하게 주목할 만한 성장을 한 1건에서 30이 빗나갔다.

🎯 같은 플랫폼의 다른 지표에서도 같은 성질이 보인다

같은 배치 Qwen-Image-2.1-viggle-turbo: 수집기 downloads 101,512(09:00~09:10 수집) → 볼트 재조회 133,151(09:1x) = +31,639 / +31.2%. 🔴 수십 분에 31%는 실제 다운로드 증가로 설명하기 어렵다 — HF 다운로드 카운터도 연속이 아니라 배치 갱신일 가능성이 높다. 📌 볼트 드리프트 처리 규약이 플랫폼별로 달라야 한다는 결론:

  • GitHub ★: 관측 범위 −1 ~ +9. “시점 차이이며 오류 아님” 처리가 타당하다.
  • HF downloads: 오늘 +31.2% 관측. “시점 차이”로 넘길 크기가 아니다.
  • HF githubStars: 캐시. 드리프트가 아니라 출처 차이다. ⚠️ 함의: HF 다운로드 기반 배수 계산(예: 원본-파생-역전 의 2.52배)은 표시된 자릿수만큼 정밀하지 않다. 배수를 소수 둘째 자리까지 적는 관행을 재검토해야 한다.

볼트 절차 (확정)

  1. 부속 GitHub 는 HF 값을 받은 뒤 GitHub API 로 반드시 재조회한다. 오늘 수집기가 pos-sae-latents·robocode 에서 이미 이렇게 했고 일치를 확인했다 — 절차가 작동한다.
  2. HF 중계값을 기록할 때 (HF 캐시) 를 병기한다.
  3. HF downloads 드리프트는 절대값과 %를 함께 적고, 10% 초과면 별도 표시한다.
  4. ⬜ 미확인: HF 캐시 갱신 주기. 09-26→09-27 에 12→91 이므로 최소 하루 1회 이상은 갱신되나 주기를 모른다.
