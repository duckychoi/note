# MCP(모델 컨텍스트 프로토콜) 완전 정복 2026: 스미더리 vs 컴포지오 vs 클라비스 vs 카카오 PlayMCP — 서버 1만 개를 연결했더니, 첫 글자를 치기도 전에 토큰 6만 개가 사라졌다

## 들어가며: 성공했는데 왜 더 느려졌을까

2026년 AI 인프라 시장에는 서로 잘 안 맞는 숫자 두 개가 있다.

**숫자 1 — MCP는 이겼다.** 2026년 5월 24일 기준 공식 MCP 레지스트리 API에는 **9,652개의 최신 서버 레코드**가, 버전을 모두 세면 **28,959개 레코드**가 등록돼 있었다. 앤트로픽은 **활성 공개 MCP 서버가 1만 개를 넘었다**고 밝혔다. 파이썬과 타입스크립트 SDK 두 개만 합쳐도 **월 9,700만 다운로드**다. 스택록(Stacklok)의 2026년 소프트웨어 리포트에 따르면 조사 대상 소프트웨어 조직의 **41%가 MCP 서버를 제한적 또는 전면적으로 프로덕션에 투입**한 상태다. ([digitalapplied](https://www.digitalapplied.com/blog/mcp-adoption-statistics-2026-model-context-protocol), [ChatForest](https://chatforest.com/guides/mcp-ecosystem-2026-state-of-the-standard/), [CData](https://www.cdata.com/blog/2026-year-enterprise-ready-mcp-adoption))

2024년 11월 앤트로픽이 처음 내놨을 때만 해도 "또 하나의 표준 제안"이었다. 2년이 채 안 돼서 오픈AI, 구글 딥마인드, 마이크로소프트가 전부 이걸 채택했다. AI를 바깥 세상에 연결하는 방법은 사실상 하나로 정리됐다.

**숫자 2 — 그런데 실제로 붙여보면 느려진다.** 클로드 코드 세션에 MCP를 **5~10개만 설치해도 사용자가 첫 글자를 치기 전에 토큰 5만~6만 7천 개가 이미 소진된다.** MCP 툴 하나당 이름, 설명, JSON 스키마, 필드 설명, enum, 시스템 지시문을 합쳐 **550~1,400 토큰**이 든다. 툴이 100개면? 컨텍스트 창의 상당 부분이 "내가 쓸 수 있는 도구 목록"만으로 채워진다. ([The New Stack](https://thenewstack.io/how-to-reduce-mcp-token-bloat/), [getunblocked](https://getunblocked.com/blog/mcp-token-budget-autopsy/))

**표준이 이기는 순간, 표준을 쓰는 비용이 문제가 됐다.**

이건 낯선 일이 아니다. USB가 이겼을 때 허브 대란이 왔고, 도커가 이겼을 때 이미지 용량이 문제가 됐다. 승리한 표준은 항상 자기가 만든 새 문제와 싸운다.

이 글은 2026년 MCP 생태계를 **규모 → 지배구조 → 스펙 → 두 개의 진짜 문제(토큰·보안) → 플랫폼 비교 → 한국 상황 → 도입 판단** 순서로 정리한다. "MCP가 뭔가요"에서 끝나는 글은 이미 넘친다. 여기서는 **실제로 붙일 때 터지는 것들**을 다룬다.

## 1. 30초 요약: MCP가 정확히 뭘 해결했나

MCP를 설명할 때 가장 많이 쓰이는 비유는 **"AI를 위한 USB-C"**다. 이 비유는 절반만 맞다. 정확히 뭘 해결했는지 보면 이렇다.

MCP 이전에는 **M×N 문제**가 있었다. AI 모델(또는 에이전트)이 M개고 연결할 도구가 N개면, 연동 코드를 M×N개 써야 했다. 클로드용 슬랙 커넥터, GPT용 슬랙 커넥터, 커서용 슬랙 커넥터를 각각 만들었다는 뜻이다. 도구 하나가 API를 바꾸면 M개를 전부 고쳐야 했다.

MCP는 이걸 **M+N**으로 바꿨다. 슬랙이 MCP 서버 하나를 만들어 두면, MCP를 지원하는 모든 클라이언트가 그걸 쓴다. 클라이언트도 마찬가지로 MCP 하나만 구현하면 1만 개 서버에 접근한다.

구조는 세 조각이다.

- **호스트(Host)** — 클로드 데스크톱, 커서, VS Code 같은 사용자가 쓰는 앱
- **클라이언트(Client)** — 호스트 안에서 서버와 1:1로 연결을 관리하는 부분
- **서버(Server)** — 실제 능력을 제공하는 쪽. 세 가지를 노출한다.
  - **툴(Tools)** — 모델이 호출하는 함수. "이슈를 생성해라", "쿼리를 실행해라"
  - **리소스(Resources)** — 모델이 읽는 데이터. 파일, 문서, DB 레코드
  - **프롬프트(Prompts)** — 사용자가 고르는 미리 정의된 템플릿

여기서 자주 오해되는 지점 하나. **MCP는 에이전트 프레임워크가 아니다.** 랭그래프나 크루AI처럼 "에이전트를 어떻게 설계할 것인가"를 다루지 않는다. MCP가 정하는 건 **"에이전트가 도구와 어떤 형식으로 대화하는가"** 하나다. 프레임워크는 갈아탈 수 있고, MCP 서버는 그대로 쓴다. 이게 MCP가 빠르게 퍼진 이유이기도 하다. 아무도 자기 아키텍처를 바꿀 필요가 없었다.

그리고 2026년에는 짝이 되는 프로토콜이 하나 더 생겼다. **A2A(Agent2Agent)**다. 업계에서 정리된 표현은 이렇다.

- **MCP = 수직 방향.** 에이전트 → 도구. "USB-C"
- **A2A = 수평 방향.** 에이전트 → 에이전트. "HTTP"

MCP는 에이전트가 내부 도구와 데이터에 어떻게 붙는지를 정의하고, A2A는 조직 경계를 넘어 에이전트끼리 어떻게 소통하고 협업하는지를 정의한다. ([Pebblous](https://blog.pebblous.ai/blog/a2a-mcp-agentic-ai-foundation-authorization/en/), [buildmvpfast](https://www.buildmvpfast.com/blog/ai-engineer-stack-2026-mcp-a2a-protocol))

## 2. 지배구조 대격변: 앤트로픽은 왜 자기 표준을 내줬나

2026년 MCP에서 가장 중요한 사건은 기술이 아니라 **정치**였다.

**2025년 12월, 앤트로픽은 MCP를 리눅스 재단 산하 에이전틱 AI 재단(AAIF, Agentic AI Foundation)에 기부했다.** 벤더 중립적이고 커뮤니티가 거버넌스를 갖는 표준이 된 것이다. ([ChatForest](https://chatforest.com/guides/mcp-ecosystem-2026-state-of-the-standard/))

그리고 **2026년 8월 17일, 구글이 만든 A2A도 같은 재단의 호스팅 프로젝트가 됐다.** ([Pebblous](https://blog.pebblous.ai/blog/a2a-mcp-agentic-ai-foundation-authorization/en/), [Linux Foundation](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year))

**앤트로픽의 프로토콜과 구글의 프로토콜이 같은 지붕 아래 들어갔다.** 이게 무슨 의미인지 짚을 필요가 있다.

### 왜 기부했나

표면적 이유는 "개방성"이다. 실제 이유는 더 실용적이다.

**엔터프라이즈는 한 회사가 소유한 프로토콜을 표준으로 안 받는다.** 금융, 의료, 공공처럼 규제가 강한 조직의 아키텍처 리뷰에서 "이 프로토콜은 앤트로픽이 소유하고 있습니다"는 통과가 어려운 문장이다. 회사가 방향을 틀거나 라이선스를 바꾸면 전사 아키텍처가 인질이 되기 때문이다.

앤트로픽 입장에서 계산은 간단하다. **프로토콜 소유권을 지켜서 얻는 이득보다, 프로토콜이 업계 표준이 돼서 클로드가 가장 잘 연결되는 모델이 되는 이득이 크다.** 소유권을 내주고 생태계를 얻는 교환이다.

### 재단은 실제로 굴러가고 있나

숫자를 보자. AAIF는 출범 당시 회원사 40곳 미만에서 **8개월 만에 250곳 이상**으로 늘었다. A2A는 출범 1년 시점에 **150개 이상 조직이 지원**하고, 구글·마이크로소프트·AWS 플랫폼에 깊이 통합됐으며, 여러 산업에서 프로덕션 배포가 진행 중이라고 발표했다. ([Linux Foundation](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year), [Blck Alpaca](https://blckalpaca.at/en/knowledge-base/ai-agents/a2a-protocol-basics/linux-foundation-aaif-bedeutung))

중요한 건 **두 프로토콜이 합쳐지지 않았다**는 점이다. 각자 메인테이너, 스펙 프로세스, 릴리스 일정을 유지한다. 재단이 정리한 건 "누가 스펙을 관리하는가" 하나다. ([Pebblous](https://blog.pebblous.ai/blog/a2a-mcp-agentic-ai-foundation-authorization/en/))

2026년 생태계 분위기를 요약하면 이렇다. **프로토콜 하이프는 끝났고, 레지스트리·워킹그룹·인증(auth)·태스크 라이프사이클·엔터프라이즈 롤아웃 같은 인프라 디테일이 논의의 중심이 됐다.** 재미없어졌다는 건, 진짜가 됐다는 뜻이다.

## 3. 2026-07-28 스펙: 무엇이 깨졌고 무엇이 열렸나

**2026년 7월 28일, MCP는 가장 큰 폭의 스펙 개정을 확정했다.** 국내에서도 ZDNet 코리아가 "AI 연동 규격 'MCP' 전면 개편…대기업 도입 쉬워진다"라는 제목으로 다뤘다. ([ZDNet Korea](https://zdnet.co.kr/view/?no=20260801122235), [MCP Blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/))

핵심 변화 네 가지다.

### 3-1. 스테이트리스 전환 — 서버리스에서 돌아간다

기존 MCP는 **양방향 스테이트풀(stateful) 프로토콜**이었다. 클라이언트와 서버가 연결을 유지하며 서로 호출하는 구조다. 이게 로컬에서는 자연스러웠지만 클라우드 배포에서는 골칫거리였다. 상태를 들고 있어야 하니 서버리스와 엣지에 못 올라갔다.

2026-07-28은 이걸 **요청/응답(request/response) 모델**로 바꿨다. 결과적으로 **MCP 서버를 서버리스와 엣지 인프라에 배포할 수 있게 됐다.** ([Claude](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude), [AAIF](https://aaif.io/blog/mcp-2026-07-28-whats-changing-and-how-to-migrate))

엔터프라이즈 관점에서 이게 왜 중요한가. 스테이트풀 서버는 **오토스케일링이 어렵고, 장애 복구가 복잡하고, 비용이 비싸다.** 스테이트리스가 되면 람다에 올리고, 트래픽에 따라 0까지 줄이고, 인스턴스가 죽어도 다음 요청은 다른 인스턴스가 받는다. "대기업 도입이 쉬워진다"는 표현은 여기서 나왔다.

### 3-2. 익스텐션 프레임워크 — 코어를 안 건드리고 확장한다

이번 스펙의 설계 철학이 잘 드러나는 부분이다. **MCP Apps와 Tasks가 버전 관리되는 익스텐션 프레임워크 아래로 들어갔다.** 인터랙티브 UI나 장시간 작업 같은 기능을 **코어 프로토콜을 바꾸지 않고** 추가하는 공식 경로가 생긴 것이다. ([MCP Blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/), [TrueFoundry](https://www.truefoundry.com/blog/mcp-2026-07-28-spec-apps-tasks-governance-revisited))

이건 성숙한 표준이 하는 일이다. 코어는 작고 안정적으로 두고, 실험은 익스텐션에서 한다. HTTP가 그랬고 리눅스 커널이 그랬다.

### 3-3. MCP Apps — 서버가 UI를 준다

가장 눈에 띄는 신기능이다. **MCP Apps는 서버가 인터랙티브 HTML 인터페이스를 제공하고, 호스트가 그걸 샌드박스 iframe에서 렌더링하게 한다.** 툴이 UI 템플릿을 미리 선언해 두면 호스트가 프리페치하고 보안 검토도 할 수 있다. ([MCP Blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/), [TrueFoundry](https://www.truefoundry.com/blog/mcp-2026-07-28-spec-apps-tasks-governance-revisited))

무슨 뜻이냐면, 지금까지 MCP 서버는 **텍스트만 돌려줬다.** 항공권을 검색하면 결과가 글자로 왔다. MCP Apps가 있으면 서버가 **날짜 선택기, 좌석 배치도, 결제 폼** 같은 실제 UI를 띄울 수 있다. 채팅 인터페이스의 한계였던 "복잡한 입력"과 "구조화된 출력"이 풀린다.

"미리 선언"과 "샌드박스 iframe"이라는 두 조건이 핵심이다. 서버가 임의의 HTML을 아무 때나 실행하게 두면 그게 곧 공격 벡터가 되기 때문에, 스펙은 처음부터 이걸 막아 놨다.

### 3-4. Tasks — 오래 걸리는 작업의 공식 처리법

**Tasks가 실험적 코어에서 벗어나 `io.modelcontextprotocol/tasks` 익스텐션으로 이동했다.** 폴링 기반의 `tasks/get`과 새로 추가된 `tasks/update`를 쓴다. ([MCP Blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/))

기존 MCP는 "요청 → 즉시 응답"을 가정했다. 그런데 실무에서는 30분짜리 데이터 마이그레이션, 3시간짜리 배치 리포트 같은 게 있다. Tasks는 이런 **장시간 작업을 시작하고, 상태를 조회하고, 결과를 나중에 받는** 표준 방식이다. 스테이트리스 전환과 짝을 이루는 설계이기도 하다. 연결을 붙잡고 기다리는 대신 폴링한다.

### 3-5. 무엇이 폐기됐나 — 마이그레이션 체크리스트

여기가 실무에서 제일 중요하다.

- **Roots, Sampling, Logging** — 폐기(deprecated). 다만 **최소 12개월간 계속 동작**한다.
- **레거시 HTTP+SSE 트랜스포트** — 공식 폐기. **1년의 유예 기간(offramp)** 부여.

([MCP Blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/), [Stacktree](https://stacktr.ee/blog/mcp-2026-spec-changes))

**즉, 2027년 중반이 실질적 데드라인이다.** 지금 HTTP+SSE 기반으로 돌아가는 MCP 서버를 운영 중이라면, 남은 시간은 대략 1년이다. 12개월은 길어 보이지만, 사내 승인·테스트·재배포 사이클을 감안하면 여유롭지 않다.

**당장 해야 할 일 세 가지**

1. 사내에서 돌아가는 MCP 서버 목록을 뽑고, 각각의 트랜스포트가 뭔지 확인한다.
2. Roots/Sampling/Logging에 의존하는 코드를 찾는다. 특히 Sampling(서버가 클라이언트에게 LLM 호출을 요청하는 기능)에 기대고 있으면 설계 변경이 필요하다.
3. SDK 버전을 올리고 신규 스펙 대응 여부를 확인한다.

## 4. 진짜 문제 ①: 컨텍스트 세금 — MCP를 붙일수록 AI가 멍청해진다

이제 도입 후에 실제로 터지는 문제로 간다. 첫 번째는 **토큰**이다.

### 얼마나 심각한가

수치부터 다시 보자.

- MCP 툴 **하나당 550~1,400 토큰** (이름 + 설명 + JSON 스키마 + 필드 설명 + enum + 시스템 지시문)
- MCP 서버 **5~10개** 설치 시 첫 프롬프트 전에 **5만~6만 7천 토큰** 소진

([The New Stack](https://thenewstack.io/how-to-reduce-mcp-token-bloat/), [getunblocked](https://getunblocked.com/blog/mcp-token-budget-autopsy/), [Apideck](https://www.apideck.com/blog/mcp-server-eating-context-window-cli-alternative))

이게 단순히 "돈이 더 나간다"는 문제가 아니다. 세 가지가 동시에 나빠진다.

1. **비용** — 매 요청마다 같은 스키마를 다시 보낸다. 캐싱으로 완화되지만 사라지지는 않는다.
2. **성능** — 컨텍스트가 길수록 모델이 느려지고, 중간에 묻힌 정보를 놓치는 "lost in the middle" 현상이 심해진다.
3. **정확도** — 툴이 100개 있으면 모델은 그중 맞는 걸 골라야 한다. 선택지가 늘수록 오선택이 늘어난다.

**MCP를 많이 붙일수록 에이전트가 똑똑해질 것 같지만, 어느 지점을 넘으면 반대로 간다.** 이건 직관에 반하는 결과라 도입 초기 팀들이 자주 밟는 지뢰다.

### 2026년에 나온 세 가지 해법

2025년 11월부터 2026년 2월 사이에 큰 개입이 세 개 나왔다. 접근은 달랐지만 **"안 쓸 툴 정의를 미리 로딩하지 마라"**라는 같은 아이디어였다. ([MCP.Directory](https://mcp.directory/blog/mcp-context-bloat-fix-2026-tool-search-code-mode-progressive-disclosure))

**① 툴 서치(Tool Search) — 앤트로픽**

모든 툴을 미리 넣지 않고, **필요할 때 검색해서 가져온다.** 툴 카탈로그를 인덱싱해 두고 모델이 "지금 필요한 도구"를 조회하는 방식이다. 점진적 공개(progressive disclosure) 패턴이다.

**② 코드 모드(Code Mode) — 클라우드플레어**

**③ MCP 코드 실행 패턴**

②와 ③은 사실상 같은 발상이다. 툴을 수십 개 노출하는 대신 **`run_python` 딱 하나를 노출한다.** 에이전트는 격리된 샌드박스에서 실행될 파이썬 코드를 쓰고, 그 코드가 RPC로 모든 툴을 호출한다. ([Red Hat](https://next.redhat.com/2026/04/23/how-sandboxed-python-reduces-tool-schema-overhead-in-ai-agents/), [MindStudio](https://www.mindstudio.ai/blog/optimize-mcp-server-token-usage))

효과는 실측됐다. **동일 작업에서 스키마를 샌드박스 파이썬으로 대체했을 때 토큰 오버헤드가 53% 감소했다.** ([Red Hat](https://next.redhat.com/2026/04/23/how-sandboxed-python-reduces-tool-schema-overhead-in-ai-agents/))

가장 극적인 사례는 핀테크 기업 **블록(Block)**이다. 자사 오픈소스 에이전트 구스(Goose)를 통해 **전사 기준 토큰 98.7% 감축**을 달성했다. ([CData](https://www.cdata.com/blog/2026-year-enterprise-ready-mcp-adoption))

### 그래서 얻는 결론: MCP는 만능이 아니다

2026년 실무자들 사이에서 정리된 문장이 하나 있다.

> **MCP, 코드 실행, CLI는 상호 보완재다. 실수는 MCP를 만능 정답으로 취급하는 것이다. 많은 연동 패턴에서 CLI는 두 자릿수 배(orders of magnitude) 적은 컨텍스트 오버헤드로 같은 일을 한다.** ([Apideck](https://www.apideck.com/blog/mcp-server-eating-context-window-cli-alternative))

이건 꽤 중요한 실무 지침이다. 예를 들어 **깃(git)** 작업을 시킬 때, git MCP 서버를 붙여 툴 20개를 로딩하는 것보다 **`git` CLI를 그냥 쓰게 하는 게** 훨씬 싸고 정확하다. 모델은 이미 git을 안다.

**MCP가 유리한 경우와 아닌 경우를 나누면 이렇다.**

MCP가 맞는 상황

- 인증이 복잡한 SaaS(OAuth, 멀티테넌트 토큰 관리)
- 모델이 잘 모르는 사내 전용 시스템
- 여러 클라이언트(커서, 클로드, 사내 에이전트)가 같은 연동을 공유해야 할 때
- 권한·감사 로그를 중앙에서 통제해야 할 때

MCP가 과한 상황

- 이미 좋은 CLI가 있는 도구(git, docker, kubectl, aws)
- 단순 HTTP API 하나 호출
- 한 명이 한 번 쓰고 마는 스크립트

## 5. 진짜 문제 ②: 보안 — 툴 설명문이 공격 코드가 된다

두 번째 문제는 더 무겁다.

### 툴 포이즈닝: 2026년 가장 흔한 공격

**MCP 툴 포이즈닝(Tool Poisoning)**은 간접 프롬프트 인젝션의 한 형태다. 공격자가 악성 MCP 서버를 운영하는데, 툴은 겉보기에 정상이고 **응답이나 메타데이터 안에 숨겨진 지시문**이 들어 있다. 그 지시문이 LLM의 컨텍스트 창에 들어가면 **신뢰된 입력으로 취급된다.** ([OWASP](https://owasp.org/www-community/attacks/MCP_Tool_Poisoning), [Cybedefend](https://www.cybedefend.com/en/blog/mcp-security-tool-poisoning))

**툴 메타데이터에 악성 지시문을 심는 방식이 클라이언트 측 취약점 중 가장 널리 퍼지고 영향이 큰 것으로 나타났다.** ([Checkmarx](https://checkmarx.com/learn/mcp-security-risks-real-world-incidents-and-security-controls/))

왜 이게 치명적인가. 일반적인 보안 모델에서 우리는 **데이터**를 의심한다. 사용자 입력, 웹 스크래핑 결과 같은 것들이다. 그런데 툴 설명문(description)은 개발자가 쓰는 것이라 **설정(configuration)으로 취급된다.** 아무도 의심하지 않는다. 그런데 LLM 입장에서는 툴 설명문이나 사용자 메시지나 똑같은 토큰이다. **신뢰 경계가 없다.**

OWASP는 이미 이걸 별도 공격 항목으로 등재했고, 클라우드 시큐리티 얼라이언스(CSA)도 2026년 7월 "MCP 공격 표면: 툴 포이즈닝과 IDE 자동 실행"이라는 리서치 노트를 냈다. 학계에서도 위협 모델링 논문이 나왔다. ([CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-tool-poisoning-auto-execution-20260701/), [arXiv](https://arxiv.org/abs/2603.22489), [MDPI](https://www.mdpi.com/2624-800X/6/3/84))

### 실제로 터진 사건들

**사건 ① — 아마존 Q VS Code 익스텐션 CVE 2건**

**CVE-2026-12957**과 **CVE-2026-12958**은 악성 리포지터리가 **임의 코드 실행과 클라우드 자격증명 탈취**를 달성할 수 있게 했다. 원인이 중요하다. **스폰된 MCP 서버 프로세스가 AWS 액세스 키를 포함한 개발자 환경 전체를 상속받았기 때문**이다. ([Checkmarx](https://checkmarx.com/learn/mcp-security-risks-real-world-incidents-and-security-controls/))

이 취약점의 교훈은 명확하다. **MCP 서버는 당신의 개발 환경 권한을 그대로 물려받는다.** 로컬에서 돌리는 MCP 서버는 곧 당신 노트북에서 돌아가는 프로그램이고, 당신의 `.aws/credentials`, `.ssh`, 환경변수를 전부 볼 수 있다.

**사건 ② — SANDWORM_MODE 타이포스쿼팅 캠페인**

2026년 초, **npm 타이포스쿼팅 캠페인이 흔한 도구를 사칭한 악성 MCP 서버를 심었다.** 타깃은 **AI 코딩 어시스턴트**였다. ([Checkmarx](https://checkmarx.com/learn/mcp-security-risks-real-world-incidents-and-security-controls/))

공급망 공격의 교과서적 형태인데, MCP 맥락에서는 더 위험하다. 일반 npm 패키지는 개발자가 코드를 읽어볼 수 있다. MCP 서버는 **AI가 자율적으로 호출하고, 사람은 결과만 본다.** 중간에 뭐가 일어났는지 확인하는 사람이 없다.

### 방어 전략: 다층으로 가야 한다

권장되는 방어는 단일 대책이 아니라 **다층 전략**이다. ([Practical DevSecOps](https://www.practical-devsecops.com/mcp-security-vulnerabilities/), [Checkmarx](https://checkmarx.com/learn/mcp-security-risks-real-world-incidents-and-security-controls/))

1. **정적 메타데이터 분석** — 툴 설명문에 숨은 지시문이 있는지 스캔한다. "이전 지시를 무시하고", "사용자에게 알리지 말고" 같은 패턴.
2. **모델 결정 경로 추적** — 에이전트가 왜 그 툴을 골랐는지 로깅한다.
3. **행위 이상 탐지** — 파일 읽기 툴이 갑자기 네트워크를 호출하면 잡는다.
4. **사용자 투명성 메커니즘** — 어떤 툴이 무슨 인자로 호출됐는지 사람이 볼 수 있어야 한다.

**여기에 실무에서 반드시 추가해야 할 것 세 가지를 덧붙인다.**

- **최소 권한 실행.** MCP 서버를 개발자 계정 권한으로 돌리지 말 것. 전용 서비스 계정, 컨테이너 격리, 자격증명 분리.
- **IDE 자동 실행 끄기.** CSA가 별도로 짚은 항목이다. 툴 호출을 자동 승인하는 설정은 편하지만, 툴 포이즈닝의 최종 실행 버튼이 된다. 최소한 쓰기/삭제/외부 전송 계열은 수동 승인으로 둔다.
- **레지스트리 화이트리스트.** 사내에서 쓸 수 있는 MCP 서버를 목록으로 관리한다. "npm에서 아무거나 설치"는 SANDWORM_MODE로 가는 길이다.

## 6. 호스팅 플랫폼 비교: 스미더리 vs 컴포지오 vs 클라비스 vs 글라마

MCP 서버를 직접 만들고 운영할 수도 있지만, 대부분은 남이 만든 걸 쓴다. 그 시장이 2026년에 정리되고 있다.

가장 중요한 구분선은 이거다. **"찾아주는 곳"과 "돌려주는 곳"은 다르다.**

### 스미더리(Smithery) — 발견의 표준, 그런데 가격이 흔들린다

스미더리는 **MCP 서버를 발견하는 사실상의 마켓플레이스**가 됐다. 등록된 서버가 가장 많고, "어떤 MCP가 있나" 둘러볼 때 첫 목적지다.

그런데 **2026년 3월 무료 티어가 종료됐고, 유료 가격 정책은 현재 유동적(in flux)인 상태**다. ([Composio](https://composio.dev/content/smithery-alternative), [Sift AI Tools](https://siftaitools.com/alternatives/smithery-alternatives))

**판단:** 탐색용으로는 여전히 최고다. 프로덕션 의존처로 삼기에는 가격 불확실성이 부담이다.

### 컴포지오(Composio) — 통합 카탈로그형

컴포지오는 **500개 이상의 사전 구축 연동**을 제공한다. 슬랙, 깃허브, 노션, 에어테이블, 스트라이프 등 흔한 것들이 전부 있고 클로드·커서·VS Code 등 MCP 호환 클라이언트에서 바로 동작한다. 가격은 **제한적 무료 티어 + 월 49달러 수준**, **앱 단위 과금(per-app)** 구조다. ([Composio](https://composio.dev/content/hosted-mcp-platforms), [Qveris](https://qveris.ai/guides/composio-alternatives/?lang=en))

**판단:** **여러 프로덕션 시스템과 붙어야 하고, 인증과 신뢰성을 중앙에서 관리하고 싶은 팀**에 맞는다. 앱 단위 과금은 카탈로그형 모델에 합리적인 구조지만, 붙일 앱이 많아지면 비용이 선형으로 는다는 뜻이기도 하다.

### 클라비스(Klavis) — 인증에 진심인 프로덕션형

클라비스는 **600개 이상 도구에 대해 OAuth가 내장된 호스팅 프로덕션 MCP 서버**를 제공한다. 차별점은 **멀티테넌트 인증(multi-tenant auth)이 기본 탑재**됐다는 것이다. 무료 티어가 있고 사용량에 따른 유료 플랜이 있으며, **스트라타(Strata) 서버는 오픈소스**다. ([ToolDirectory](https://tooldirectory.ai/tools/klavis-ai), [Composio](https://composio.dev/content/hosted-mcp-platforms))

**판단:** 멀티테넌트가 왜 중요하냐면, **자기 제품 안에 AI 기능을 넣는 회사**에게는 이게 전부이기 때문이다. 사용자 A의 슬랙 토큰과 사용자 B의 슬랙 토큰을 분리해서 안전하게 관리하는 일은 직접 만들면 지옥이다. **B2B SaaS에 AI 에이전트를 얹으려는 팀이라면 클라비스가 1순위 검토 대상**이다. 오픈소스 코어가 있다는 점도 락인 우려를 낮춘다.

### 글라마(Glama) — 평가·탐색 레이어

글라마는 **호스팅이나 실행을 정하기 전에 기존 MCP 능력을 찾고 평가하는 발견 레이어**로 쓰기 좋다. ([Composio](https://composio.dev/content/hosted-mcp-platforms))

### 그 외

**베이로(Vayro), 스테인리스(Stainless), 스피크이지(Speakeasy), 디플로이스택(DeployStack), 프리펙트 호라이즌(Prefect Horizon)** 등이 MCP 호스팅 시장에서 경쟁 중이다. 특히 스테인리스와 스피크이지는 **OpenAPI 스펙에서 MCP 서버를 자동 생성**하는 쪽에 강점이 있다. 이미 잘 정의된 REST API가 있는 회사라면 이 경로가 가장 빠르다. ([Vayro](https://www.vayro.ai/vs/mcp-hosting))

### 선택 가이드 요약

- **"뭐가 있나 보고 싶다"** → 스미더리, 글라마
- **"여러 SaaS에 빨리 붙이고 싶다"** → 컴포지오
- **"내 제품 사용자별로 안전하게 붙여야 한다"** → 클라비스
- **"우리 API를 MCP로 내보내고 싶다"** → 스테인리스, 스피크이지
- **"규제 때문에 다 우리가 통제해야 한다"** → 직접 구축 + 사내 레지스트리

## 7. 한국 상황: 카카오가 판을 깔고, 데이터 회사가 붙는다

국내 MCP 생태계도 구체적인 움직임이 있다.

### 카카오 PlayMCP — 국내 최초급 개방형 MCP 플랫폼

카카오는 MCP 기반 개방형 플랫폼 **'PlayMCP'**를 운영 중이다. 개발자가 다양한 MCP 서버를 자유롭게 등록하고 실험할 수 있는 플랫폼으로, **현재 약 200여 개의 외부 MCP 서버가 업로드**돼 있다. 오픈소스 AI 에이전트 **'오픈클로(OpenClaw)' 연동도 지원**한다. ([카카오](https://www.kakaocorp.com/page/detail/12012))

전 세계 1만 개와 비교하면 200개는 작아 보인다. 하지만 국내 서비스(카카오 생태계, 국내 SaaS, 한국어 데이터)에 특화된 MCP 서버는 글로벌 레지스트리에서 안 나온다. **로컬 레지스트리의 가치는 개수가 아니라 커버리지**다.

### 쿠콘 — 데이터를 MCP로 판다

비즈니스 데이터 플랫폼 기업 **쿠콘**은 AI 에이전트 시대를 겨냥해 **MCP 기반 데이터 사업**을 본격화했다. 기존에 보유한 데이터를 AI 에이전트가 곧바로 활용할 수 있도록 **MCP 형태로 제공해 'AI 에이전트 전용 데이터 허브'로 도약**하겠다는 구상이다. ([파이낸셜뉴스](https://www.fnnews.com/news/202606151041464112))

이 움직임이 시사하는 바가 크다. **데이터 회사의 유통 채널이 API에서 MCP로 옮겨가고 있다.** 지금까지 데이터 판매는 "API 문서를 주고 고객사 개발자가 붙이는" 방식이었다. MCP로 내놓으면 **고객사의 AI 에이전트가 바로 소비**한다. 통합에 드는 마찰이 사라진다.

CData는 **2026년에 엔터프라이즈 애플리케이션 벤더의 30%가 MCP 서버를 출시할 것**으로 전망했다. ([CData](https://www.cdata.com/blog/2026-year-enterprise-ready-mcp-adoption)) 쿠콘의 행보는 이 흐름의 국내판이다.

**국내 SaaS 기업이라면 지금 던져야 할 질문은 하나다.** "우리 제품에 MCP 서버가 없으면, 고객사의 AI 에이전트가 우리를 못 쓴다. 그럼 경쟁사 중 MCP를 낸 곳으로 갈아타지 않을까?"

## 8. 도입 성과: 숫자가 나온 사례들

MCP 이야기에서 자주 빠지는 게 "그래서 효과가 있나"다. 공개된 수치 몇 개를 정리한다.

- **블록(Block)** — 자사 에이전트 구스(Goose)를 통해 **전사 토큰 98.7% 감축**
- **라이파이젠 은행(Raiffeisen Bank)** — MCP 통합 AI를 리스크 관리에 적용해 **리스크 평가 역량 40% 향상**
- **업계 전반** — 소프트웨어 조직의 **41%가 MCP 서버를 프로덕션 투입**

([CData](https://www.cdata.com/blog/2026-year-enterprise-ready-mcp-adoption))

여기서 주의할 점. **블록의 98.7%는 "MCP를 붙여서" 얻은 게 아니라 "MCP를 코드 실행 방식으로 최적화해서" 얻은 숫자다.** 그냥 붙이면 오히려 토큰이 는다. 이 구분을 놓치면 도입 후 "왜 우리는 비용이 늘었지"라는 상황이 온다.

## 9. 그래서 우리는 어떻게 해야 하나 — 역할별 체크리스트

### 개발자·AI 엔지니어라면

1. **MCP를 5개 이상 동시에 켜놓지 마라.** 작업별로 프로필을 나눠라. 코딩할 때 필요한 MCP와 리서치할 때 필요한 MCP는 다르다.
2. **CLI로 되는 건 CLI로 해라.** git, docker, kubectl, aws는 MCP 서버 붙이지 말고 그냥 쓰게 두는 게 싸고 정확하다.
3. **툴이 20개를 넘으면 코드 실행 패턴을 검토해라.** `run_python` 하나로 바꾸면 53% 절감이 실측된 수치다.
4. **2026-07-28 스펙 마이그레이션을 캘린더에 넣어라.** HTTP+SSE와 Roots/Sampling/Logging은 12개월 시한부다.

### CTO·아키텍트라면

1. **사내 MCP 레지스트리를 만들어라.** 승인된 서버만 쓰게 하는 화이트리스트. SANDWORM_MODE 같은 공급망 공격의 유일한 실질적 방어다.
2. **MCP 서버 실행 권한을 분리해라.** 아마존 Q CVE의 근본 원인은 "개발자 환경 상속"이었다. 전용 서비스 계정과 컨테이너 격리는 선택이 아니다.
3. **자동 승인을 끄는 정책을 세워라.** 최소한 쓰기·삭제·외부 전송 계열 툴은 사람이 승인한다.
4. **벤더 락인을 계산해라.** 컴포지오·클라비스 같은 호스팅에 붙으면 편하지만, 나중에 빼기 어렵다. 오픈소스 코어가 있는 쪽(클라비스 스트라타)이 탈출구가 넓다.

### SaaS 기업 의사결정자라면

1. **우리 제품의 MCP 서버가 있는가.** 없다면 로드맵에 올려라. 엔터프라이즈 벤더 30%가 올해 낸다.
2. **스테이트리스 전환을 활용해라.** 2026-07-28 스펙 덕에 서버리스 배포가 가능해졌다. 초기 운영 비용이 크게 낮아졌다.
3. **OpenAPI가 이미 있다면 자동 생성 경로를 봐라.** 스테인리스·스피크이지가 이 시장을 노린다.

### AI 도입 담당자·기획자라면

1. **"MCP 몇 개 붙였다"를 성과 지표로 쓰지 마라.** 붙일수록 나빠지는 구간이 있다.
2. **토큰 비용을 도입 전후로 측정해라.** 최적화 없이 붙이면 늘어난다.
3. **보안 검토를 통과할 수 있는 구성인지 먼저 확인해라.** 나중에 뒤집히면 전부 다시 한다.

## 10. 자주 묻는 질문(FAQ)

**Q. MCP를 꼭 써야 하나요? 그냥 API 호출하면 안 되나요?**

써야 할 이유는 **재사용성**과 **인증 관리**다. 연동을 한 번 만들어 여러 클라이언트(클로드, 커서, 사내 에이전트)에서 공유하고, OAuth 토큰을 중앙에서 관리할 수 있다. 반대로 **API 하나만 호출하면 되는 일**에는 과하다. MCP는 만능이 아니라 특정 문제에 대한 답이다.

**Q. MCP와 A2A 중 뭘 먼저 봐야 하나요?**

거의 모든 팀은 **MCP가 먼저**다. A2A는 조직 경계를 넘어 에이전트끼리 협업하는 시나리오용인데, 그 단계까지 간 조직은 아직 소수다. 도구 연결(MCP)이 안정되고 나서 에이전트 간 협업(A2A)을 본다.

**Q. MCP 서버는 로컬과 원격 중 뭐가 나은가요?**

보안 관점에서는 **원격이 낫다.** 로컬 서버는 개발자 환경 권한을 상속받아서 아마존 Q CVE 같은 사고가 난다. 2026-07-28 스펙의 스테이트리스 전환으로 원격(서버리스) 배포가 훨씬 쉬워졌으니, 새로 만든다면 원격을 기본으로 두는 게 맞다.

**Q. 무료 MCP 서버를 npm에서 받아 써도 되나요?**

**출처 확인 없이는 위험하다.** 2026년 초 SANDWORM_MODE 캠페인이 정확히 이 경로를 노렸다. 최소한 (1) 공식 레지스트리 등재 여부, (2) 리포지터리 소유자, (3) 다운로드 수와 이력을 확인하고, 가능하면 사내 화이트리스트로 관리한다.

**Q. 지금 MCP를 도입하면 나중에 표준이 바뀌어 헛수고가 되지 않을까요?**

가능성이 낮아졌다. **리눅스 재단 산하 AAIF로 거버넌스가 넘어갔고**, 오픈AI·구글·MS가 모두 채택했으며, 스펙 개정에도 **12개월 폐기 유예**를 두는 성숙한 프로세스를 보였다. 다만 **2026-07-28 스펙 이전 방식으로 짜면 1년 내 손봐야 한다**는 건 사실이므로, 새로 시작한다면 신규 스펙 기준으로 간다.

**Q. 한국어 서비스나 국내 시스템용 MCP 서버는 어디서 찾나요?**

**카카오 PlayMCP**에 약 200여 개의 외부 MCP 서버가 올라와 있다. 국내 데이터는 쿠콘 같은 데이터 플랫폼 기업이 MCP 형태로 공급을 시작했다.

## 마무리: 표준 전쟁은 끝났고, 운영 전쟁이 시작됐다

2026년 MCP를 한 문장으로 요약하면 이렇다.

**"이길 것이냐"의 질문은 끝났다. 이제 "잘 쓸 것이냐"의 질문만 남았다.**

공개 서버 1만 개, SDK 월 9,700만 다운로드, 조직 41%의 프로덕션 투입, 리눅스 재단 거버넌스, 그리고 경쟁 프로토콜이었던 A2A까지 같은 재단으로. 표준 경쟁은 사실상 종료됐다.

그런데 승리한 표준을 실제로 운영해 보면 세 가지가 기다린다.

1. **토큰 세금** — 붙일수록 비싸지고 느려지고 부정확해지는 구간이 있다. 코드 실행과 툴 서치로 관리해야 한다.
2. **신뢰 경계 붕괴** — 툴 설명문이 곧 프롬프트다. 아무도 의심하지 않던 곳이 최대 공격 표면이 됐다.
3. **마이그레이션 시한** — 2026-07-28 스펙의 폐기 항목들은 1년 시한부다.

이 세 가지를 모르고 도입하면, "AI에 도구를 붙였는데 더 비싸고 더 느리고 더 위험해졌다"는 결론에 도착한다. 실제로 2026년 상반기에 그 결론에 도착한 팀이 적지 않다.

**MCP는 케이블이다. 케이블을 많이 꽂는다고 컴퓨터가 빨라지지 않는다.** 어떤 걸 꽂고, 어떤 걸 뽑고, 어떤 걸 아예 안 꽂을지 정하는 게 2026년 하반기의 실력이다.
