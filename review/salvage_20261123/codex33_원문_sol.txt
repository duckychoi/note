대가의 문장(편집 권고): 짧은 평서문, 구체적 주어("The observer gain is computed …"), 주장 바로 뒤에 근거(식·정리·표·그림 번호),
단위 있는 수치, 수식이 말하는 것을 문장으로 되풀이하지 않기, 한계는 방어하지 않고 사실로 적기.
표본에 흔한 "It can be seen that", "obviously", "efficaciously", "is testified", "the effectiveness of the proposed method is verified"
(뒤 셋은 발췌 판독에서 본 표현 — 빈도는 재지 않음)는 문법상 틀리지 않지만 반복하면 상투적으로 읽힌다 — 위 표의 상한 안에서만 쓴다.

### 1-1. 저자·학술지별 특징 (위 표본에서 실측 — 집필할 때 어느 쪽을 본뜰지 정하는 근거)

## 2. TCYB 원고 골격 (TCYB 2020+ 21편 — 편집 권고, 연구 내용에 맞게 조정 가능)

숫자는 `corpus_style_stats.py` 출력이다. '발췌 판독'이라고 쓴 것은 2020년 이후 TCYB 약 15편의 절 제목·서론·기여·결론·Remark 문단을
직접 읽고 본 경향이다 — 스크립트로 재현되는 수치가 아니다.

- **절 구성(발췌 판독):** I. INTRODUCTION / II. PRELIMINARIES AND PROBLEM FORMULATION(또는 PROBLEM DESCRIPTION AND PRELIMINARIES) / III. MAIN RESULTS
  (또는 설계와 안정성 분석을 두 절로) / IV. SIMULATION (EXAMPLES / RESULTS) / V. CONCLUSION. 읽은 논문 대부분이 이 틀이었다.
- **초록: 150~200단어 (의무).** 근거: TCYB 저자 안내(SMC 학회, `https://www.ieeesmc.org/?p=4823` = `https://www.ieeesmc.org/publications/transactions-on-cybernetics/information-for-authors-3/`,
  2026-11-03 열람)는 B.9항에서 "150-250 words", B.4항에서 "100 to 250 word"라고 해 **페이지 안에서 서로 다르다** — 엄격한 쪽(150)을 하한으로 쓰고,
  상한 200은 사용자의 10쪽 규칙에 맞춘 값이다. 실측: TCYB 2020+ 21편 중앙 157, 범위 94~252, 150 미만 10편·200 초과 2편(게재본도 범위를 자주 벗어난다).
  흐름: "This article addresses …" → 핵심 난제 → "To overcome these challenges, we develop …" → "It is proven that …" → 검증 문장(무엇으로, 무엇보다 얼마나).
- **서론:** 분야 배경(인용 묶음) → 기존 방법의 한계 단락("However, these methods assume …") 2~3개 → "Motivated by the above analysis, this article …"
  (21편 중 13편이 "Motivated/Inspired by the above …"를 쓴다) → 난제 2~3개 → "The main contributions are summarized as follows." 뒤 번호 목록(21편 중 14편).
  - 기여 개수: 번호를 셀 수 있었던 15편에서 3개 10편·2개 3편·4개 2편. **3개**로 쓴다(4절).
  - "Notation:" 단락은 21편 중 10편 — 기호가 많으면 서론 끝에 둔다.
  - 절 안내 단락("The remainder of this article is organized as follows")은 21편 중 5편뿐이다 — **10쪽 원고에서는 생략**한다.
  - "few results … / has not been studied" 식 공백 서술은 6편. 쓰면 공백을 구체적으로("no existing result handles X and Y simultaneously [a], [b]") 적는다.
- **기여 문장:** 비교형. "Compared with [refs], which …, this article …" / "Unlike [refs] that assume …, the proposed …".
  "first"·"novel" 대신 **무엇이 기존 대비 달라졌는지**(가정 완화, 동시 설계, 보장의 종류)를 쓴다. 발췌 판독한 TCYB 기여 목록에도 이 형식이 많았다
  ("Compared with" 2.5/3.6, 21편 전부 사용).
- **정리·Remark:** TCYB 2020+ 중앙값[25~75%] Theorem 2[1~3], Lemma 2[1~3], Assumption 2[1~3], Remark 5[3~7]. 가정은 Assumption 번호로 명시하고,
  정리 뒤 해석·가정 정당화·기존 결과와의 차이는 Remark로 쓴다(발췌 판독: "Unlike [refs] …", "Assumption 1 indicates …"로 여는 Remark가 흔했다).
- **시뮬레이션:** 설정(모델·파라미터·초기값·외란) → 비교 대상과 튜닝 방법 → 결과(그림·표) → 해석. TCYB 2020+ 그림 11[8~13.5], 표 1[0~2].
  RMS·IAE 같은 정량 지표를 쓴 편은 5/21뿐이다 — 정량 비교표가 있으면 차별점이 된다(단 표는 3개 이하, 3절).
- **결론:** "In this article, we have …" 또는 현재완료 서술(21편 중 14편이 현재완료) 한 단락 + 향후 과제 한 문장(14편). 새 수치·새 주장 금지.

## 3. 분량 배분 — 10쪽 (사용자 규칙, 의무)

**공식 규정:** TCYB 저자 안내(위 2절 주소, 2026-11-03 열람) — "Regular papers are normally about 10 Transactions pages in length,
or shorter", **10쪽을 넘는 쪽마다 $175 초과 쪽 요금(의무)**. 즉 사용자의 10쪽 규칙은 TCYB 정규 논문 기준과 같다. 'Transactions pages'는 최종 조판 쪽이라
IEEEtran 양식으로 컴파일한 투고 원고 쪽수와 다를 수 있다(차이 크기는 미확인 — 여유 0.5쪽을 두는 이유). IEEE Author Center의 TCYB 개별 안내 페이지는 확인하지 않았다(미확인).

## 4. 동기·기여·novelty를 돋보이게

- 서론 첫 두 단락 안에 **"왜 기존 방법으로는 안 되는가"**를 구체적 현상(수치·물리적 이유)으로 보인다.
- 기여는 3개 이내, 각 기여가 본문의 정리·식·그림 번호와 1:1로 대응해야 한다(대응 안 되는 기여는 지운다).
- 비교 결과는 **방향과 크기**로 쓴다("reduces the RMS error from 70.2 mm to 10.3 mm"). 퍼센트만 단독으로 쓰지 않는다.
- 비교 대상은 문헌 그대로의 형태와, 공정성을 위해 같은 조건으로 튜닝한 형태를 함께 둔다. 튜닝판에 지는 조건이 있으면 짧게 적고,
  우리 방법이 이기는 축(보장의 종류, 설계의 체계성, 파라미터 민감도)을 그 옆에 둔다 — 변호사식 배치(0절 6항).

## 5. 수식·논리 검증 (원고 수정마다, 의무)

1. **기호 일관성:** 정의 전 사용 금지, 같은 기호 두 의미 금지, 차원(벡터/행렬 크기) 확인.
2. **유도 재확인:** 핵심 식(동역학, 오차 동역학, 리야프노프 미분, LMI)은 손으로 또는 기호 계산(sympy 등)으로 다시 유도한다.
3. **정리-가정-시뮬레이션 대응:** 정리의 가정이 시뮬레이션 조건(포화, 지연, 이산화, 필터, 불연속 외란)을 덮는지 확인한다.
   안 덮으면 그 사실을 Remark에 적고, 그 조건의 결과는 정리가 아니라 시뮬레이션 근거로만 주장한다(0절 6항).
4. **수치는 로그에서 스크립트로, 근거는 보관:** 원고의 모든 숫자·표·그림은 실행 로그에서 스크립트로 만들고, 원고와 로그를 대조하는 스크립트로 확인한다.
   손으로 옮겨 적지 않는다. **원고가 인용하는 수치의 원자료 로그와 생성 스크립트는, 재생성 시간과 상관없이 원고 제출(또는 사용자가 폐기를 지시할 때)까지 보관한다**
   (하위 지침의 '30분 미만이면 생성 명령만 남김' 규칙보다 우선). 경로는 연구노트·README에 적는다.
5. **교차검수:** 자기 검증만으로 "검증됨"을 선언하지 않는다. codex로 반박 검수를 받는다 —
   모델 `gpt-6.2-sol`(안 되면 `gpt-6.1-sol`, 그다음 `gpt-6-astra`; 사용량 한도면 대체하지 말고 기다리거나 사용자에게 알림).
   검수 관점: ①수치(원고↔로그) ②주장(근거 있는가) ③공정성 ④문체(1절) ⑤이론(가정·유도). 판정과 라운드 수를 사용자에게 그대로 보고한다.
   예: `codex exec -m gpt-6.2-sol -s read-only --skip-git-repo-check -o <out.md> - < prompt.txt`

## 6. 작업 환경 (이 컴퓨터에서 확인된 것)

- **OneDrive 충돌:** 다른 PC에서 같은 파일을 고치면 `파일명-<PC이름>.tex`(예: `main_single-HD-home.tex`) 사본이 생긴다.
  원고를 고치기 전에 같은 폴더에 충돌 사본이 있는지 보고, 있으면 diff로 두 변경을 병합한 뒤 사용자에게 알린다. 한쪽을 덮어쓰지 않는다.
  줄바꿈(CRLF/LF)은 원본 것을 유지한다.

## 7. 보고 (사용자에게)

한국어, 결론 먼저, 수치 근거(파일:라인, 로그 값). 원고에 쓴 방식과 무관하게 **불리한 결과·실패·검수 지적을 모두** 보고한다.
확인하지 않은 것은 "미확인"이라고 쓴다. 건너뛴 단계는 건너뛰었다고 쓴다.

**설명 형식 (2026-11-03 사용자 승인 — "이번 설명 좋다, 앞으로도 이런 식으로"):** 정리·실험·검수 결과를 설명할 때 이 순서를 따른다.
1. 첫 줄에 질문에 대한 직답("네, 정리 3이 맞습니다")과 한 문장 요지.
2. **기존 것 / 새로 생긴 것**을 나눠 쓴다. 원고에 있는 것은 `파일:라인`으로, 원고 밖(노트·실험)은 파일 경로로 위치를 밝힌다.
3. 정리·기법은 번호만 쓰지 말고 **역할 이름 + 표 한 줄**(무엇을 보장하나 / 비유)로 소개한다. 비유는 개념마다 한 줄
   (예: "과녁 하나를 정해 두고 한 걸음씩 다가가기", "출발 전 일기예보 vs 달리면서 계기판으로 남은 연료 계산").
4. 수치는 **기존 → 새 값 비교표**로, 말로 방향과 크기를 붙인다("0.13 s → 0.46–0.72 s, 약 4배 길어짐").
5. 한계는 따로 모아 굵게 적는다(무엇을 못 보장하나, 코드에 없는 것).
6. 끝에 "정리하면" 세 줄(무엇이 그대로 / 무엇이 새로 / 추천과 사용자 결정 필요 사항).
전문용어는 그대로 두되 첫 등장 때 쉬운 말로 한 번 풀고, 반례·핵심 메커니즘은 숫자 한 예로 보인다(예: 0 → 1/2 → −1/4).

**쉬운 문장 규칙 (2026-11-03 사용자 지시 — "전혀 못 알아먹겠다. 초보자도 단번에 술술 읽히게"). 의무.**
이 규칙은 위 적용 범위와 달리 **두 경로(`CHD`, `바이브꿀팁`)와 그 하위 폴더의 모든 작업**에서 사용자에게 보고할 때 적용한다(연구·원고가 아닌 작업 포함).
1. 초보자가 한 번 읽고 알아듣게 쓴다. 다 쓴 뒤 "처음 보는 사람이 막힘 없이 읽나?"를 스스로 점검한다.
2. 한 문장에는 한 가지 내용만 담는다. 길어지면 문장을 나눈다. "~하고, ~이며, ~해서"로 길게 잇지 않는다.
3. 어려운 명사를 줄줄이 붙이지 않는다. 나쁜 예: "최소 간격 예산 제한 하 계수 교환 이득 유지 여부". 좋은 예: "계수를 드물게 보내도 효과가 남는지 봤습니다."
4. 내부 이름(가설 B1, `rho`, `coefChan`, 시드 번호, 파일 이름)을 본문 설명에 쓰지 않는다. 꼭 필요하면 쉬운 말 뒤 괄호에 한 번만, 또는 맨 끝 "근거 위치"에만 둔다.
5. 숫자는 꼭 필요한 것만 쓰고, 바로 뒤에 뜻을 붙인다("4.1 mm로, 교환을 안 할 때보다 1.9 mm 줄었습니다").
6. 표는 짧게(3~4열, 칸에는 짧은 말). 표만 던지지 말고 표 앞에 한두 문장으로 무엇을 보면 되는지 말한다.
7. 순서: 한 줄 결론 → 무엇을 해 봤나(쉬운 말) → 결과(쉬운 말 + 짧은 표) → 약점 → 이제 할 수 있는 것.
위 설명 형식(1~6)과 부딪치면 이 쉬운 문장 규칙이 우선한다. 정확성(불리한 결과·미확인 표기)은 그대로 지킨다.

## 8. 도구

- `paper_style_check.py` (이 폴더): `.tex`(분할 원고의 `\input`·`\include` 포함)와 컴파일된 `.pdf`를 **함께** 준다.
  표현·초록·쪽수의 의무 판정은 PDF 출력 텍스트로 하고(매크로·조건부 영역 등 소스 표기와 무관), TeX 소스는 입력 파일·환경 수 점검에 쓴다.
  `.tex`만 주면 표현·초록은 참고(`?`)로만 나온다.
  - 투고처: `--venue tcyb`(기본), `--venue automatica`, `--venue tie`(this article 의무, 초록 참고, 실험 절 제목 의무, 10쪽). automatica면 'this paper'가 정상이고 'this article'·초록 단어 수는 `?`로만 본다
    (Automatica 공식 초록 제한은 확인하지 않음 — 미확인).
  - `!` = **의무 위반**(종료 코드 1): 1절에서 근거가 '사용자 지정'인 금지 표현, (tcyb) 'this paper', (tcyb) 초록 150~200단어 밖, PDF 10쪽 초과,
    펼치지 못한 `\input`(누락·순환). 반드시 고친다. PDF에서 References 제목이나 초록을 못 찾으면 판정 없이 종료 코드 2(원고 위반이 아니라 추출 실패).
    알 수 없는 인자(`-`로 시작하는 옵션, .tex·.pdf를 두 개씩 준 경우 포함)도 종료 코드 2.
  - 초록은 1~2쪽 텍스트 블록에서 각주(Manuscript received, 소속, DOI 등) 블록을 빼고 'Abstract'(Elsevier는 'a b s t r a c t')부터 Index Terms·Keywords·
    Introduction·© 앞까지로 잡는다(`pdftext_common.py`, 통계 스크립트와 공유 — 고칠 때는 이 파일 하나만 고친다).
  - `?` = **권고 참고**(종료 코드에 영향 없음): 1절 상한(novel 3, It is worth/should be noted 2, It can be seen/observed 2, obviously/clearly 2,
    본문 em-dash 1 — IEEE 양식의 "Abstract—"·"Index Terms—"·"Note to Practitioners—"는 빼고 센다), 'remarkable'(근거 유무는 사람이 판단),
    문장 첫머리 'In summary'/'Overall'(마무리 문장인지는 사람이 판단 — 마무리 문장이면 1절에 따라 고친다), Remark 3개 미만(TCYB 하위 25%),
    표 3개 초과, 본문 굵은 글씨, 같은 단락의 Furthermore/Moreover 중복.
    내용상 이유가 있으면 그대로 두고 사용자에게 이유를 보고한다. 권고를 맞추려고 필요 없는 Remark를 만들거나 유용한 표를 지우지 않는다.
  - 검사기는 보조 도구다 — 통과가 곧 문체 합격은 아니다.
  `C:\ProgramData\miniforge3\python "C:\Users\user\OneDrive\최신할일\논문작성\CHD\paper_style_check.py" main.tex main.pdf [--venue automatica]`
- `corpus_style_stats.py` (이 폴더): 1~3절 실측값 재현(5개 참고 폴더, DOI·해시 중복 제거, 학술지 판별, 그룹별 분포, 기여 번호 개수,
  실험 절 제목, 연도별 article/paper, 초록 추출 실패·제외 목록). 참고 논문 폴더에 논문이 추가되면 다시 돌려 표를 갱신한다.
  인자로 폴더를 주면 그 폴더만 센다. 5개 폴더 전체는 몇 분 걸린다. 알려진 한계: TAES 등 일부 양식은 초록을 못 잡는다(실패 목록에 출력, IEEE 2020+ 8편).

- `pdftext_common.py` (이 폴더): 위 두 스크립트가 공유하는 PDF 처리(합자·하이픈, 각주를 뺀 초록 추출, 양식 em-dash 제거).
