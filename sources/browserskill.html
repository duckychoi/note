핵심 인사이트 — 발명은 자동화가 아니라 소유권 분리다

기존 브라우저 자동화는 “에이전트에게 브라우저를 준다” 였다. 이건 반대다 — 에이전트는 자기 창(Agent Window)에 격리되고, 사용자 탭은 명시적으로 빌린 뒤 반납한다. 3단 경유 구조: bsk CLI → 로컬 데몬 → 크롬 확장. 🎯 에이전트가 브라우저와 직접 통신하는 경로가 없다. → 해결하는 문제는 “로그인을 어떻게 통과하나”가 아니라 “이미 로그인된 세션을 어떻게 방해 없이 공유하나” 다. 카드 설명 그대로: “without interrupting your work”. → 에이전트-웹접근 의 접근 층에 대한 세 번째 답이다. browser-use 는 조작 층, camofox-browser·CloakBrowser 는 지문 위조로 접근 층을 풀었다. 이건 위조하지 않는다 — 진짜 세션을 빌린다. 🎯 지문 문제가 원리적으로 발생하지 않는 유일한 노선.

🔴 지원 범위 — "지원"과 "예상"이 카드 안에서 갈린다

실제 지원 명시: OS는 macOS·Linux·Windows x64, 브라우저는 Chrome·Edge만. Firefox는 계획 단계. 🔴 한정어 보존: “other Chromium-based browsers are expected to work when they support unpacked Chromium extensions” — 지원이 아니라 예상이다. 조건절까지 붙어 있다(unpacked extension 허용 시). → 인용할 때 “모든 Chromium 브라우저 지원” 으로 옮기면 저자가 쓰지 않은 말이 된다 → 한정어-탈락 🔴 캡차·로그인 시 human-in-loop 전환은 주장만 확인됐고 구현은 미확인이다(수집기 자기신고, 볼트도 코드 미확인).

도메인별 추출 (ai-news)

  • 신뢰도: ★4,740 · MIT · 3개월차 · 당일 커밋. 기준(1000+ 또는 당일 급상승) 양쪽 다 충족. 🔴 벤치마크·성공률 수치는 0개(366행 README, 전 섹션 헤딩 10개 스캔 완료).
  • 즉시 활용: YES — 단 조건부. Chrome 사용자면 오늘 쓸 수 있고, 셸 호출 가능한 에이전트면 프레임워크 무관하다(Claude Code 포함). 🔴 다만 내 워크플로우의 실익이 불분명하다 — 이 위키 인제스트는 로그인 세션이 필요 없는 공개 API·공개 페이지가 대부분이다. 로그인 장벽이 있는 소스를 다루기 시작할 때가 도입 시점.
  • 6개월 영향력: 🎯 “에이전트용 브라우저를 따로 띄운다”는 전제가 흔들린다. 헤드리스 브라우저를 별도 실행하면 세션·쿠키·2FA를 전부 다시 푸는데, 이 노선은 그 전부를 건너뛴다. 접근 층 비용이 0에 가까워지면 조작 층(모델 능력)만 남는다.
  • 대체 관계: browser-use 를 대체하지 않는다 — 앞단에 붙는다. browser-use는 “무엇을 클릭할지”, 이건 “어느 브라우저에서”. 🔴 반면 지문 위조 계열(camofox-browser·CloakBrowser)과는 경합이다 — 진짜 세션을 쓰면 위조가 필요 없다.
  • 허와 실: ✅ 마케팅이 얇은 편이다. 카드 설명이 기능 서술이고(“Let AI agents use your real, logged-in browser”), 지원 범위에 expected to work 같은 한정어를 스스로 붙였다 → 자기제한-명시 의 부분 사례(범위는 밝혔으나 벤치 부재를 선언하진 않았다).
  • 액션: star + 설치 보류. 지금 당장의 병목이 아니다.

당장 할 것

star 하고 Firefox 지원 진행을 분기별로 확인한다. 내 환경이 Chrome 고정이 아니면 도입 조건이 안 된다.

미해결 질문

“탭 빌림/반납”이 코드로 강제되는가, 관례인가. 격리가 이 프로젝트의 전부인데 강제 메커니즘을 README 수준에서 확인할 수 없다. 만약 관례라면 에이전트가 사용자 탭을 반납하지 않고 점유하는 실패 모드가 열린다. → 볼트도 코드 미확인, 수집기도 미확인. 둘 다 못 본 지점이다.
