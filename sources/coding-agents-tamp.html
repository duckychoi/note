Coding Agents for Generalized Task and Motion Planning Problems

🎯 핵심 인사이트 — 에이전트가 계획을 세운 게 아니라, 계획하는 프로그램을 써서 동결시켰다

TAMP(task and motion planning)는 이산 결정이 기하·운동학·동역학 제약과 강결합돼 어렵다. generalized TAMP 는 인스턴스 간 규칙성을 이용해 부담을 줄이지만 기존 방법은 TAMP 전용 엔지니어링을 많이 요구한다. 질문: 코딩 에이전트가 인스턴스를 넘어 일반화되는 프로그램을 합성해 그 과정을 자동화할 수 있는가. 실험 설계가 이 논문의 신뢰도를 만든다:

  • 과제 설명 + 시뮬레이터 접근권만 준다(플래너도 도메인 지식도 주지 않음)
  • 각 에이전트가 고정된 합성 예산 안에서 환경과 상호작용하는 방식을 스스로 고른다
  • 🎯 프로그램을 동결(freeze) 해 미지 인스턴스에서 평가한다 📌 “동결”이 결정적이다. 에이전트가 테스트 시점에 추론하면 “에이전트가 잘한다” 가 되지만, 프로그램을 동결하면 “에이전트가 만든 산출물이 좋다” 가 된다 — 후자가 훨씬 강한 주장이고 검증 가능하다. 비용도 분리된다(합성은 한 번, 실행은 무료). 🎯 그리고 관측이 인상적이다: 로그상 에이전트가 상호작용으로 물리 모델을 캘리브레이션하고 엣지케이스를 시험하며 전략을 다듬는 것이 보였다. 이건 ExplorationBench(같은 배치)가 측정하려는 바로 그 행동이며, 여기서는 실제 로봇 도메인에서 부수적으로 관측됐다.

✅ 이번 배치에서 수치가 있는 유일한 논문 — 규모가 크다

평가 대상: Claude Code (Opus 5) · Codex (GPT-5.6 Sol · GPT-6 Astra) — 3개 에이전트 구성. 환경: KinDER·PDDLStream 기반 28개 시뮬레이션 환경(원 벤치마크보다 물체 수가 많음). 규모: 생성 프로그램 980개 × held-out 인스턴스 100개 = 총 98,000 에피소드. 결과: 세 에이전트 구성 전부가 수작업 플래너·원샷 생성·LLM 기반 일반화 플래닝 베이스라인을 평균 성공률에서 앞섰다 — 56%~95% vs 플래너 47%(플래너가 존재하는 16개 환경 기준). 물체 수가 늘어도 에이전트 프로그램이 플래너보다 높은 성공률을 유지하며, 인스턴스당 평균 계산량은 한 자릿수 차수(order of magnitude) 적다. ✅ 에이전트에게 준 전체 프롬프트를 포함해 코드 전부 공개를 명시한다 → 재현 경로가 있다.

🔴 범위 수치 56%~95% 는 39%p 폭이다 — "전부 앞섰다"의 실제 모양

🎯 하단 56% 는 플래너 47% 를 9%p 넘는 수준이고 상단 95% 는 압도적이다. 즉 환경별 분산이 매우 크다. “전부 앞섰다” 는 평균 기준 주장이고, 39%p 폭은 어떤 환경에서는 간신히 이겼다는 뜻이다. 🔴 환경별 분포가 초록에 없다 — 28개 중 몇 개가 56% 대인지 모른다. ⚠️ 그리고 비교 모집단이 다르다: 에이전트는 28개 환경 전부에서 평가됐으나 플래너 대조는 16개 환경(플래너가 존재하는 것만)이다. 나머지 12개는 대조군이 없다 → 이 12개에서는 “앞섰다”를 말할 수 없다. 비매칭-비교 주의 지점이며, 다만 플래너를 만들 수 없는 환경이 있다는 것 자체가 에이전트 접근의 논거이기도 하다. ✅ 결론 문장도 “strong baseline” 이라는 한정 표현이다 — 수집기가 이를 보존했다(한정어 보존 11배치 연속). 🔴 볼트 유의: 성공률만 있고 실패 양상이 없다. 로봇 도메인에서 44% 실패(56% 케이스)의 성격은 안전상 중요하다.

도메인별 추출 (slam-3dgs)

🔀 도메인 재판정 — raw ai-news → slam-3dgs

근거: slam-3dgs 도메인 정의가 “로봇 SLAM / 3DGS / 카메라” 이고 TAMP 는 로봇 조작 계획의 핵심 문제다. KinDER·PDDLStream 은 로봇 플래닝 벤치이며 기하·운동학·동역학 제약을 다룬다. 09-17 ActionPiece 재판정(VLA → slam-3dgs)과 같은 근거다.

  • 현재 SOTA: 🟡 이 논문이 주장하는 바로는 “손으로 만든 플래너가 더 이상 상한이 아니다” 다. 🔴 단 절대 SOTA 수치가 아니라 상대 비교이고, 비교 대상이 이 논문이 고른 베이스라인이다. KinDER·PDDLStream 의 공식 리더보드와 대조하지 않았다(⬜ 미확인).
  • 실시간 가능성: 🎯 동결된 프로그램이므로 추론 오버헤드가 없다 — 이것이 실시간 관점의 최대 이점이다. 인스턴스당 계산량이 플래너보다 한 자릿수 차수 적다는 주장은 실시간성에 직접 유리하다. 🔴 단 절대 시간(ms/fps)이 초록에 없다 — “30fps+ 가능한가”에 답할 수 없다.
  • 카메라 파이프라인: ⬜ 해당 없음/미확인. 시뮬레이터 상태 접근 기반으로 보이며 실제 카메라 입력을 쓰는지 초록에 없다. 순수 상태 기반이면 실기 이전이 별개 문제로 남는다 — 이 논문의 가장 큰 미확인 지점이다.
  • 응용 가능성: 🎯 볼트에 직접 연결점이 있다 — 평가 대상이 Claude Code (Opus 5) 다. 사용자 본인 하니스와 같은 도구가 “프로그램 합성기” 로 쓰여 로봇 플래너를 이겼다. 즉 이 방법론의 도구 요구사항을 볼트는 이미 갖고 있다(시뮬레이터가 없을 뿐).
  • 필수 레퍼런스: tomsilver/robocode(★13) + arXiv 2609.30233. 프롬프트 전문이 공개돼 있다는 것이 가장 실용적인 부분이다 — 코드보다 프롬프트가 이전 가능성이 높다 → actionable: 프롬프트 설계만 추출.
