핵심 인사이트 — README가 자기 위험을 전용 섹션으로 판다

대부분의 에이전트 하네스는 “한 줄로 설치하세요” 에서 멈춘다. openrig 는 거기서 한 걸음 더 간다 — rig setup --dry-run 을 먼저 돌리라고 권하고, “OpenRig 가 당신의 머신에서 무엇을 바꾸는지” 를 별도 섹션으로 두고, 백업을 권고한다. 프로바이더 훅과 워크스페이스 신뢰 설정을 건드린다고 명시한다. 🎯 자기제한-명시 의 오늘 사례다. 같은 배치 hindsight 가 “내 점수는 제3자 재현, 남의 점수는 자기보고” 로 신뢰 구조를 밝혔다면, openrig 는 부작용 범위를 밝힌다. 밝히는 대상이 다르지 며 둘 다 같은 태도다. 📌 이게 왜 실용적으로 중요한가: 볼트는 코드 실행 0건이 10배치 연속이다. 설치를 미루는 이유 중 하나가 “내 환경에 뭘 하는지 모른다” 인데, openrig 는 그 질문에 설치 전에 답하는 몇 안 되는 레포다. 실행 장벽을 README가 직접 낮췄다.

구조 — 하네스의 하네스

YAML로 에이전트 팀을 정의하고 rig up 한 줄로 부팅한다. tmux 위에 Claude-Code 와 Codex 좌석을 띄우고 owner · checker 역할로 나눠 한 시스템처럼 관리한다. 리드 에이전트에게 목표를 말하면 전문가 좌석에 분배한다. 요구사항: Node 20/22/24 + tmux 필수. 설치 npm i -g @openrig/cli. 🎯 핵심은 “에이전트를 만든다”가 아니라 “이미 있는 에이전트 CLI들을 한 팀으로 묶는다” 다 — 자기 모델을 안 만들고 좌석 관리만 한다.

  • 즉시 활용: YES — 오늘 배치에서 설치 문턱이 가장 낮다. npm i -g 한 줄 + tmux. 🔴 다만 actionable 에 등록하지 않는다 — agent-browser·superpowers 가 각각 5일·3일째 미실행 이월이고 목록을 늘리면 신호가 죽는다. 소진이 먼저다(수집기 판단과 볼트 09-27 판단 10이 일치).
  • 6개월 영향력: 좌석(seat) 추상화가 남을 것 같다. 모델이 아니라 CLI 프로세스를 단위로 묶는다는 접근은 벤더 교체에 강하다 — Claude Code 든 Codex 든 tmux 안에서는 같은 좌석이다. 같은 배치 paperclip 이 대시보드·예산·조직도로 같은 문제를 푸는 것과 대조된다.
  • 대체 관계: paperclip 과 정면으로 겹친다. 둘 다 “여러 벤더 코딩 에이전트를 한 시스템으로”. 차이는 paperclip = 서버+웹UI+비용추적(★91,180), openrig = CLI+tmux+YAML(★1,256). 🎯 72배 스타 차이가 곧 품질 차이는 아니다 — paperclip 은 open issues 5,895, openrig 는 51 이다.
  • 허와 실: ⬜ 볼트가 실행하지 않았다. README가 정직하다는 판단은 문서에 대한 판단이지 동작에 대한 판단이 아니다. --dry-run 이 실제로 무해한지, 좌석 분배가 실제로 작동하는지 미확인.
  • 액션: ⬜ 등록 보류(위 사유). agent-browser 또는 superpowers 소진 후 재검토.
