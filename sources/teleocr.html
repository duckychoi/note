StarDoc-AI/TeleOCR

🎯 이 페이지의 최대 값은 OCR 성능이 아니라 창 길이 3번째 점추정이다

볼트는 09-23부터 HF downloads 30일 창의 실제 길이를 추정해 왔고, 09-24에 점추정 2개를 얻은 뒤 09-26에는 “HF 4건 전부 30일 미만이라 역산 표본 0건” 으로 진전이 없었다. 🎯 오늘 TeleOCR 이 이번 배치 HF 모델 3건 중 유일하게 30일보다 나이가 많다 — created 2026-08-14 = 44일 차. 그래서 downloads ≠ downloadsAllTime 이 되고 역산이 가능하다.

볼트 역산 (균일 다운로드율 가정):

  • downloads(30일) 27,837 · downloadsAllTime 39,391 · 나이 44일
  • 비율 = 27,837 / 39,391 = 70.67%
  • 균일 일평균 = 39,391 / 44 = 895.25/일
  • 함의 창 길이 = 27,837 / 895.25 = ≈31.1일

🎯 세 점추정이 좁게 모인다: Qwen3.5-9B(209일) ≈31.4일 · Ternary-Bonsai-27B-gguf(82일) ≈28.5일 · TeleOCR(44일) ≈31.1일. 나이가 44·82·209일로 4.75배 차이고 누적 규모가 39K·1.88M·65.2M 로 1,666배 차이인데 셋 다 28.5~31.4일 안에 들어오고 30일을 감싼다. 📌 등급 상승: 09-26까지 “점추정 2개, 문서 미확인” → 오늘 “독립 점추정 3개가 규모 1,666배 구간에서 수렴, 문서 여전히 미확인”. 🔴 여전히 신뢰구간이 아니다 — 균일 다운로드율 가정에 전적으로 기댄 점추정 3개다. 특히 TeleOCR 은 09-10 개명과 트렌딩 진입이 있어 다운로드가 균일했을 가능성이 낮다(후반 집중 추정). 후반 집중이면 함의 창은 실제보다 짧게 나온다 → ≈31.1일은 하한 쪽으로 편향됐을 수 있다. ✅ 부수 확인: downloads == downloadsAllTime ⟺ 30일보다 어린 저장소 규칙이 오늘 3/3 만족(viggle 5일·MiMo 6일 = 같음 / TeleOCR 44일 = 다름) → 누적 14/14 예외 없음.

🔴 카드의 "약 1.2B" 와 실측 1.415B 가 어긋난다

수집기 인용(카드 기준): “약 1.2B 파라미터 경량 문서파싱 전용 VLM”. 🎯 볼트 HF API expand[]=safetensors 실측: total = 1,415,072,768 = 약 1.42B. 차이 약 18%. 📌 가장 그럴듯한 설명은 부분 집계다 — 문서 VLM 은 보통 [언어 백본 + 비전 인코더] 구조이고, “1.2B” 가 백본만 센 값이면 비전 인코더 ~0.2B 를 더해 1.42B 가 된다. 자릿수가 맞는다. 🔴 그러나 이것은 볼트의 추정이고 카드가 그렇게 말하지 않았다. 카드 433행 중 316행이 미열람이므로 어디서 1.2B 가 나왔는지 확인되지 않았다. ⚠️ 실무 함의는 작지 않다: 경량 모델의 판매 논거가 크기이고, 대조군이 0.8B·0.9B·1B·1.2B 로 촘촘하다. 1.2B 로 적으면 MinerU2.5-Pro(1.2B)와 동급이지만 1.42B 면 가장 큰 모델이다 — 즉 “같은 크기에서 더 좋다” 와 “더 큰데 더 좋다” 의 차이다. → 단위-불일치 갱신(09-26 Ternary-Bonsai-2-27B “벤더가 자기 두 표에서 불일치” 와 같은 계열). 🔴 볼트가 정직해야 할 부분: 대조군 파라미터 수는 수집기 인용값이고 볼트가 API 로 재측정하지 않았다. 만약 대조군도 같은 방식으로 부분 집계됐다면 비교는 여전히 공정하다. 미확인이다.

🎯 성능 — 항목별로 갈리고, 강점이 "촬영 문서" 쪽에 분명하다

OmniDocBench v1.6: TeleOCR Overall 96.87 · Text Edit 0.027↓ · Formula CDM 96.36 · Table TEDS 97.05 · TEDS-S 98.52 · Read Order Edit 0.122↓ 대조군: OvisOCR2(0.8B) 96.58 · PaddleOCR-VL-1.6(0.9B) 96.33 · MinerU2.5-Pro(1.2B) 95.75 · GLM-OCR(0.9B) 95.22 · HunyuanOCR-1.5(1B) 94.74 🔴 3항목 1위 / 3항목 2위: Overall·Table TEDS·TEDS-S 는 1위지만 Text Edit(0.025) · Formula CDM(97.53) · Read Order(0.111) 은 OvisOCR2 가 앞선다. Overall 격차는 96.87 vs 96.58 = 0.29p 로 매우 작다. 🎯 Wild_OmniDocBench(촬영 문서)에서 그림이 달라진다: Overall 88.53 · Text Edit 0.1173 · Table TEDS 89.05 · TEDS-S 92.14 · Read Order 0.2011 로 5항목 1위이고 Formula CDM 88.26 만 MinerU2.5-Pro 90.15 에 밀린다. 📌 이 대비가 논문 주장과 정합한다: 기여가 “디지털 + 촬영 문서 통합” 이고 기하인식 문서 모델링·CGDP 샘플링이 왜곡 문서용 장치다. 깨끗한 문서에서는 근소하고 왜곡 문서에서 벌어진다 — 즉 주장한 곳에서 이겼다. 이건 신뢰도를 높이는 패턴이다(아무 데서나 이기는 것보다). 🎯 실무상 핵심: 왜곡 문서를 dewarping 전처리나 별도 교정 모델 없이 직접 파싱한다(DocUNet·DIR300 에서 시각 평가). 🔴 Dr.DocBench Challenge(EMNLP 2026) 자체 평가는 Overall 67.96 vs MinerU 2.5 Pro 62.26 · OvisOCR2 59.25 지만 Table TEDS 64.97 은 MinerU 67.75 에 밀리고 order edit 0.398 도 MinerU 0.356 보다 나쁘다. ⚠️ 카드가 이것이 대회 공식 순위가 아니라 벤더 자체 평가임을 스스로 밝힌다 → 자기제한-명시.

🔀 개명 — 정규명-우선-중복검사 두 번째 오늘 사례

2026-09-10 에 NaviDC-OCR → TeleOCR 로 개명했다. ✅ 볼트 중복검사를 양쪽 이름으로 수행: NaviDC 0히트 · NaviDC-OCR 0히트 · TeleOCR 0히트 · StarDoc-AI 0히트 · 부속 GitHub caipeng328 0히트 → 신규 확정. 🎯 오늘 배치에 개명이 2건이다(Model-Optimizer 2025-12-08 · TeleOCR 2026-09-10). 09-24에 볼트가 신설한 개념이 한 배치에서 두 번 쓰였다 — 개념의 사용 빈도가 예상보다 높다.

도메인별 추출 (local-llm)

🔀 도메인 재판정 — raw ai-news → local-llm

근거: 1.42B 는 local-llm 도메인의 “Small LM” 정의에 정확히 해당하고, 문서 파싱은 온디바이스 처리 수요가 큰 작업이다(문서를 클라우드로 올리지 않으려는 요구). ai-news 로 두면 소형 모델 실용성 누적에서 빠진다.

  • 실용성 판단: 🎯 이번 배치에서 실배포 가능성이 가장 높은 모델이다. 1.42B · Apache-2.0 이면 소비자 GPU·심지어 CPU 로도 돌 수 있는 규모다. 🔴 단 지연시간·메모리 수치가 카드 열람 범위에 없다 — “몇 초에 한 페이지”를 모른다. ⬜ 양자화 배포물(GGUF 등) 유무 미확인.
  • 메모리 아키텍처: 해당 없음(에이전트 메모리 아닌 지각 모델).
  • Hermes 적용: 🎯 직접 적용 후보가 있다 — 볼트 인제스트 파이프라인이 PDF·촬영 문서를 못 읽는다. 지금 볼트는 논문을 초록만 보고(오늘도 5/5 arXiv 본문 0행) 이것이 9배치 연속 최대 한계다. 🔴 그러나 arXiv 는 HTML/텍스트를 제공하므로 OCR 이 필요한 병목이 아니다 — OCR 은 스캔된 문서에 필요하다. 솔직히 말하면 지금 볼트의 병목은 OCR 부재가 아니라 본문을 열지 않는 것이다. 적용 근거를 과장하지 않는다.
  • 트레이드오프: 🎯 0.29p 를 위해 1.42B vs 0.8B(1.78배)를 쓴다 — OmniDocBench 에서는 비용 대비 이득이 나쁘다. 🎯 반면 Wild(촬영) 에서는 격차가 실질적이므로 용도가 트레이드오프를 결정한다: 깨끗한 PDF 만 다루면 OvisOCR2 가 합리적이고, 사진 문서가 섞이면 TeleOCR 이다. → 수확체감-변곡점 사례.
  • 오픈소스 구현체: 부속 GitHub caipeng328/TeleOCR · 기술보고서 arXiv 2608.12898 · Apache-2.0. 🔴 볼트가 레포·보고서 둘 다 조회하지 않았다.
